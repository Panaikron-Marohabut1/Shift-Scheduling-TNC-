# เชื่อมฐานข้อมูล Supabase — 1 พฤศจิกายน 2026

## สถานะ

Backend เชื่อมและอ่านข้อมูลจาก Supabase จริงผ่านบัญชี `tnc_backend_dev` แล้ว เปิดเว็บ/API ที่พอร์ต 3000 และ Auth ที่พอร์ต 3001 ด้วย `pnpm dev:supabase` ได้ นำการผูกบัญชีเดโม่ 3 Role และประวัติเดิม 2,045 รายการขึ้น Cloud แล้ว โดยคงตารางกะเดิมและเก็บฐานข้อมูลในเครื่องไว้

การเชื่อมต่อนี้ครอบคลุมข้อมูลที่ Backend มี API รองรับอยู่แล้ว คำขอสลับพร้อมวันคืนกะ ลา OT ย้ายวันหยุด และการแก้ข้อมูลบางส่วนที่ยังใช้ localStorage ยังไม่ได้ย้ายขึ้นฐานข้อมูลกลาง ไม่ถือว่าระบบรองรับข้อมูลกลางครบทุกฟีเจอร์หรือพร้อมใช้งานจริง

## วิธีเปิดระบบและกลับไปใช้ฐานเดิม

เปิดจากโฟลเดอร์หลักของโปรเจค โดยเตรียม dependencies และไฟล์ Auth ตาม [คู่มือหลัก](../../README.md) ก่อน

ใช้ฐานข้อมูล Supabase:

```powershell
pnpm dev:supabase
```

ใช้ฐานข้อมูล PostgreSQL ในเครื่อง:

```powershell
pnpm dev
```

เข้าเว็บที่ `http://localhost:3000` ระบบจะพาไป Login ที่ `http://localhost:3001` ตามค่าปกติ คำสั่งทั้งสองใช้พอร์ตเดียวกัน ต้องหยุดคำสั่งเดิมก่อนสลับ ค่าพอร์ตยังปรับได้ตาม `.env` และคู่มือ Auth

`pnpm dev` ยังคงเป็นค่าเดิมที่ใช้ฐานข้อมูลในเครื่อง ไม่ได้เปลี่ยนให้เลือก Cloud อัตโนมัติ ทั้งสองฐานเป็นข้อมูลคนละชุด ไม่มีการเขียนหรือซิงก์สองทาง การกลับไปเปิดฐานเดิมจึงไม่แสดงรายการใหม่ที่เพิ่งทำบน Cloud

## ขอบเขตและข้อมูล

- ใช้โปรเจค `mmesiubkvxmsklmgsepd` เพื่อพัฒนาระบบด้วยข้อมูลเดโม่เดิม วัตถุประสงค์คือให้ Backend ใช้ฐานข้อมูลกลางเดียวกัน
- คงพนักงาน ทีม Role การผูกบัญชีที่เจ้าของเคยกำหนด และกฎธุรกิจเดิม ไม่เพิ่ม Role Admin หรือเปิดผูก Microsoft อัตโนมัติ
- ข้อมูลที่เทียบมีข้อมูลพนักงานเดโม่ ตารางกะ บัญชี/Role คำขอ การอนุมัติ และประวัติ ไม่คัดลอกรหัสผ่านของ Supabase Auth หรือข้อมูล Auth sessions
- สิทธิ์ผู้ใช้แอปยังตรวจผ่าน Backend และการผูก Supabase UID กับผู้ใช้ในฐานข้อมูล บัญชีฐานข้อมูลสำหรับโปรแกรมเป็นคนละส่วนกับ Role พนักงาน
- คงหลักฐาน audit เดิม ผู้กระทำ เวลา และเวอร์ชันเดิม ไม่ลดข้อกำหนดเก็บ log อย่างน้อย 90 วัน ไม่กำหนดอายุจัดเก็บใหม่สำหรับข้อมูลพนักงาน
- อ้างอิง [กติกาโครงการ](../../AGENTS.md), [ข้อกำหนดข้อมูลและหลักฐาน](../01-requirements/rule.md), [ขอบเขตเดโม่](../02-design/prototype/alpha-demo.md) และ [ผลตรวจชุดก่อนหน้า](2026-11-01-release-check.md)

## ผลตรวจฐานข้อมูล

- ทั้งสองฝั่งมีตารางแอป 16 ตาราง รวม `schema_migrations` และ 117 คอลัมน์
- ชื่อ ชนิดข้อมูล ค่าเริ่มต้น และเงื่อนไขอนุญาตค่าว่างของคอลัมน์ตรงกัน
- Primary key, foreign key, unique และ check constraints ตรงกัน 65 รายการ หลังแยก NOT NULL ที่ PostgreSQL 18 แสดงใน catalog เพิ่มเติมออกจากการเทียบกับ PostgreSQL 17
- มี migration ของแอปครบ `001_core.sql` ถึง `004_request_cancellation.sql` ทั้งสองฝั่ง เป็นประวัติใน `public.schema_migrations`; เป็นคนละระบบกับประวัติ Supabase CLI migrations
- แต่ละฝั่งมีพนักงาน 13 ราย ผู้ใช้แอป 11 ราย ทีม 4 ทีม ตารางรายเดือน 3 รายการ และช่องตารางกะ 1,092 รายการ ค่าการทำงานตรงกัน มีเวลาสร้างข้อมูลต่างกัน
- นำการผูกบัญชีเดโม่เดิมของ `employee-a`, `supervisor-a` และ `manager` ตามไปแล้ว ไม่เปลี่ยน Role หรือสร้างผู้ใช้ Supabase Auth เพิ่ม
- คัดลอก audit เดิม 2,045 รายการโดยคง ID ผู้กระทำ เวลา ข้อมูลเดิม/ใหม่ และรายละเอียดเดิม ตรวจเทียบเนื้อหาแบบ canonical แล้ว SHA-256 ตรงกัน: `d2f97d98040b220565696df3aace86dd866df7325e178a51b130c2798d03e06d`
- ปรับลำดับเลขของ audit บน Cloud ให้ต่อจาก ID สูงสุดเดิม 2,069 เพื่อไม่ให้รายการใหม่ชน ID ที่นำเข้า จำนวนแถวกับเลข ID สูงสุดไม่จำเป็นต้องเท่ากัน
- ก่อนนำเข้า ทั้งสองฝั่งยังไม่มีคำขอสลับในฐานข้อมูล การลา OT และคำขอแบบใหม่ในเบราว์เซอร์ไม่รวมอยู่ในตัวเลขนี้ จำนวน audit บน Cloud อาจเพิ่มจากการเปิดระบบและทดสอบภายหลัง
- ขั้นตอนนำเข้าข้อมูลไม่ได้แก้ฐานข้อมูลต้นทางในเครื่อง และไม่ได้สร้างตารางกะใหม่ทับข้อมูลที่มีบน Supabase

- `local-database.dump`: สำรองฐานข้อมูลแอปในเครื่องแบบ PostgreSQL custom archive

## บัญชีและการเชื่อมต่อ

- เพิ่มคำสั่ง `pnpm dev:supabase` อ่านข้อมูลเชื่อมต่อจาก `.env.supabase.local` ที่ไม่ขึ้น Git
- หลังได้รับคำยืนยันจากเจ้าของ สร้างบัญชี `tnc_backend_dev` บน Cloud และทดสอบ Login ฐานข้อมูลพร้อม SELECT ผ่านแล้ว จึงตั้ง `SUPABASE_CONNECTION_READY=true` ในไฟล์เฉพาะเครื่อง
- บัญชี `tnc_backend_dev` แบบ LOGIN สืบทอดสิทธิ์ Backend เดิมจาก `shiftflow_app` ไม่มีสิทธิ์ superuser, สร้างฐานข้อมูล, สร้าง Role, replication หรือ bypass RLS และจำกัดการเชื่อมต่อ 8 ช่อง
- ตรวจสิทธิ์จริงแล้ว บัญชีนี้เข้า schema `auth` ไม่ได้ และ UPDATE/DELETE หลักฐาน audit ไม่ได้ การเข้าถึงข้อมูลแอปยังต้องผ่านสิทธิ์และการตรวจของ Backend ตามเดิม
- รหัสสุ่มอยู่เฉพาะไฟล์ตั้งค่าในเครื่อง การสร้างบัญชีใช้ SCRAM verifier แทนรหัสผ่านแบบอ่านออก ไม่เปลี่ยนรหัสของบัญชีเดิม ไฟล์ credential และข้อมูลสำรองถูก Git ignore
- โครง API ยังคง localhost/DEMO; การเชื่อมฐานข้อมูล Cloud ไม่ได้เปิดเว็บให้เข้าถึงจากอินเทอร์เน็ต
- คำสั่ง Cloud ไม่ส่ง owner credential ให้ runtime ส่วน `pnpm dev`, migrate, seed และ tests ที่รันแยกตามปกติยังอ่าน `.env` เดิมและใช้ฐานข้อมูลในเครื่อง

## TLS และใบรับรอง

- ใช้ Session pooler ที่อ่านจาก Connect dialog ของโปรเจค: `aws-0-ap-south-1.pooler.supabase.com:5432`
- ดาวน์โหลด CA จากลิงก์ Download certificate ใน Dashboard เป็น `config/certs/supabase-prod-ca-2021.crt` นี่เป็นใบรับรองสาธารณะ ไม่ใช่ private key
- เชื่อมต่อผ่านบัญชี Backend และ SELECT ข้อมูลจริงสำเร็จ ตรวจจาก client แล้ว `encrypted=true` และ `authorized=true` โดยยืนยันใบรับรอง ไม่ได้ปิดการตรวจ TLS
- Backend กำหนด `rejectUnauthorized=true` พร้อม CA และป้องกันตัวเลือกใน connection URI ที่อาจเขียนทับการตรวจ TLS
- Supavisor ไม่รับประกันการใช้ timezone/timeout ที่ส่งใน startup options จึงตั้งค่า session ด้วย SQL ก่อนใช้แต่ละ physical connection: UTC และ statement timeout 10 วินาที ทั้งการอ่านทั่วไปและ transaction ใช้เส้นทางนี้
- Runtime ปฏิเสธบัญชีผู้ดูแลฐานข้อมูลสำหรับการเชื่อม Cloud และไม่แสดง connection URI/รหัสผ่านในข้อความตรวจตั้งค่า
- แหล่งใบรับรอง: https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt
- SHA-256 fingerprint: `80:70:25:AD:50:D4:ED:21:9D:2C:9C:7D:29:9C:00:4F:82:4E:B0:0C:F7:F6:5A:FE:F6:07:D0:7B:72:E6:CA:FA`
- อ้างอิง [การเชื่อม Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres) และ [TLS ของ node-postgres](https://node-postgres.com/features/ssl)

## ผลทดสอบและงานถัดไป

- `pnpm check`: ผ่าน API build, JavaScript/Markdown/whitespace และตัวตรวจความปลอดภัยหน้าเว็บ 55 ไฟล์
- `pnpm test`: รันซ้ำหลังเพิ่ม session initialization แล้วผ่าน 35/35 ข้อ รวมการทดสอบการตั้งค่า TLS ใหม่ 3 ข้อ ใช้ฐานทดสอบแยกในเครื่อง ไม่สร้าง/ล้างฐานทดสอบบน Cloud
- `node scripts/audit-backlog.mjs`: PASS สำหรับ spec/backlog เดิม ไม่ได้ยืนยันกฎธุรกิจที่ยังค้าง
- `git diff --check`: ผ่าน
- การเชื่อมบัญชีฐานข้อมูล การตรวจ TLS/สิทธิ์ การอ่านข้อมูล การย้ายการผูกเดโม่ 3 บัญชี และการเก็บประวัติเดิมผ่านแล้ว
- ตรวจ `Database` class กับ Cloud จริงผ่านทั้ง `query()` และ `transaction()`: ผู้เชื่อมต่อเป็น `tnc_backend_dev`, timezone เป็น UTC และ `statement_timeout` เป็น 10 วินาที
- Cloud smoke test ผ่านทั้ง Employee, Supervisor และ Manager: Login ผ่าน Supabase Auth จริง → `/api/me` ระบุ Role ถูกต้อง → อ่านตารางพฤศจิกายน 360 ช่อง → อ่านคำขอได้สถานะ 200 → Logout → `/api/me` ตอบ 401 การตรวจนี้ไม่ได้เปลี่ยนตารางหรืออนุมัติคำขอธุรกิจ
- Security advisor ยังมีคำเตือนเดิมเรื่อง [ป้องกันรหัสผ่านที่เคยรั่วไหลยังไม่เปิด](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) ไม่มีการเปลี่ยนการตั้งค่านี้หรือรหัสเดโม่ในรอบเชื่อมต่อ และไม่ใช้ผลทดสอบนี้รับรองความพร้อมใช้งานจริงทั้งระบบ
- ขั้นถัดจากการเชื่อมต่อคือย้ายคำขอที่ยังเก็บในเบราว์เซอร์ผ่าน API ทีละประเภท ตามกฎที่ผู้เกี่ยวข้องยืนยัน แล้วค่อยทำ Realtime
- กฎธุรกิจที่ยังรอคำตอบยังคงรอการยืนยัน ไม่เปลี่ยนการอนุมัติ Admin/Manager หรือ schema คำขอใหม่ การย้าย localStorage และ Realtime เป็นงานถัดไป

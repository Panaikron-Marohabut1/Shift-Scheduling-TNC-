## โหมดที่คู่มือนี้อ้างอิง

- **ในเครื่อง (`pnpm dev`)** ใช้ฐาน PostgreSQL ของเครื่องตามค่าเริ่มต้น ส่วนการเข้าสู่ระบบใช้ Supabase Auth เมื่อกำหนดค่าไว้ เมนูเดโม่บางหน้าเก็บข้อมูลในเบราว์เซอร์
- **ฐานกลาง (`pnpm dev:supabase`)** ใช้เว็บบนเครื่องของแต่ละคนและใช้ฐานเดโม่ Supabase เดียวกัน สำหรับตาราง คำขอส่วนกลาง การอนุมัติ โควตา และการจัดการบัญชีหรือพนักงานที่เปิดสิทธิ์ไว้
- จำนวนด้านล่างนับ **เมนูที่เห็นจริงรวมแจ้งเตือน** การส่งคำขอ การอนุมัติ การค้นหา และการเปิดรายละเอียดเป็นการทำงานภายในเมนู [การตั้งค่าโหมด](../../apps/api/src/config.ts) · [รายการเมนู](../../apps/web/src/app/profiles.js) · [เมนูที่แสดงจริง](../../apps/web/src/app/shell.js)

## หน้าที่และเมนูของแต่ละบทบาท

### Employee · 5 เมนูทั้งสองโหมด

1. **กะของฉัน** ดูกะตัวเองรายเดือนหรือรายวัน เปิดรายละเอียด และยื่นจากช่องของตัวเองตามประเภทที่ใช้ได้ในวันนั้น
2. **ตารางกะ** เปิดตารางรวม A–D ดูรายเดือนหรือรายวัน และกรองทีม
3. **คำขอของฉัน** ยื่นและติดตามคำขอ แท็บ **คำขอเฉพาะฉัน** สำหรับคำขอที่กระทบตัวเอง เช่น ลาไม่มีคนแทนและ OT รายบุคคล แท็บ **คำขอร่วมกับผู้อื่น** สำหรับสลับกะและลาแบบมีคนแทน ผู้ยื่นและผู้ร่วมเห็นรายการเดียวกันโดยระบุผู้ยื่นคนเดิม การยกเลิกเป็นสิทธิ์ของผู้ยื่นตามเงื่อนไขด้านล่าง
4. **ประวัติของฉัน** ดูเวลายื่น อนุมัติ ปฏิเสธ ยกเลิก และผลการเปลี่ยนหรือคืนกะที่เกี่ยวข้อง ตารางประวัติแสดงกะก่อนและหลังเฉพาะของผู้ที่เปิดดู กด **ดูคำขอ** เพื่อเปิดรายการต้นทาง
5. **แจ้งเตือน** ดูแจ้งเตือนของบัญชีตัวเอง

### Supervisor · 6 เมนูทั้งสองโหมด

1. **ตารางกะ** ดูตารางรวมและเลือกทีม
2. **กะของฉัน** ดูกะตัวเองและยื่นคำขอของหัวหน้ากะ
3. **ภาพรวมกำลังพล** ดูคนเข้ากะเช้าและกะดึก วันหยุด ลา และ OT ของวันที่เลือก
4. **คิวคำขอตรวจสอบ** ดูคำขอที่ตนได้รับมอบหมายและคำขอที่ตนมีส่วน กดอนุมัติหรือปฏิเสธตามสายอนุมัติ หากปฏิเสธต้องใส่เหตุผล ระบบตรวจบัญชีผู้อนุมัติ บทบาท และทีมที่รับผิดชอบอีกครั้งตอนบันทึก คำขอที่หัวหน้ากะยื่นเองออกไปให้ Manager พิจารณา
5. **ประวัติการเปลี่ยนแปลง** ดูรายการที่เกี่ยวข้องตามสิทธิ์และเปิดรายละเอียดคำขอได้จากรายการที่เชื่อมไว้
6. **แจ้งเตือน** ดูรายการที่ส่งถึงบัญชีตัวเอง

### Manager · 5 เมนูในเครื่อง และ 5 เมนูบนฐานกลางเดโม่เมื่อเปิดสิทธิ์จัดการคน

1. **ติดตามสถานะคำขอ** ติดตามคำขอและอนุมัติหรือปฏิเสธรายการที่ระบบกำหนดให้ Manager พิจารณา เช่น คำขอของหัวหน้ากะ ข้อมูลคำลาฐานกลางเปิดตามความเกี่ยวข้องหรือการได้รับมอบหมาย
2. **พนักงานและทีม** จัดการพนักงานและหัวหน้ากะได้ทุกทีม A–D เปลี่ยนตำแหน่งงานและบทบาทระหว่าง Employee กับ Supervisor และย้ายทีมแบบระบุวันที่มีผล เปลี่ยนตำแหน่งหรือบทบาทมีผลเมื่อบันทึก ส่วนการย้ายทีมรักษาทีมและตารางก่อนวันมีผล ระบบห้ามย้ายย้อนหลัง ห้ามซ้อนการย้ายที่รอมีผล และแจ้งรายการที่กระทบเมื่อคำขอที่ยังมีผลขัดกับการย้ายหรือเปลี่ยนสิทธิ์
3. **ตารางรายปี** ในเครื่องใช้ดูและตั้งค่าตารางรายปีเดโม่ เช่น รูปแบบกะและวันหยุด ในฐานกลางเมนูตำแหน่งนี้เป็น **ตารางกะ** สำหรับดูตารางส่วนกลาง
4. **ตั้งค่าระบบ** ในเครื่องมีหน้าตั้งค่าเดโม่และโควตาสลับกะ บนฐานกลางใช้เมนู **โควตาสลับกะ** สำหรับดูค่าที่มีผลและบันทึกค่าสำหรับเดือนถัดไป
5. **แจ้งเตือน** ดูรายการที่ส่งถึงบัญชีตัวเอง เช่น คำขอที่ต้องตรวจ

เมื่อโหมดปิดสิทธิ์จัดการคน Manager จะเห็น 4 เมนู การมอบบทบาทเริ่มต้นของบัญชีใหม่อยู่ที่ Admin [การจัดการพนักงาน](../../apps/api/src/people-management/people-management.service.ts) · [ตารางรายปี](../../apps/web/src/features/manager/annual.js) · [โควตาส่วนกลาง](../../apps/api/src/requests/swap-quota.service.ts)

### Admin · 2 เมนูสำหรับบัญชี Admin เดโม่ที่อนุญาต

1. **กำหนดบทบาท** ดูผู้รอสิทธิ์และให้บทบาทเริ่มต้นเป็น Employee, Supervisor หรือ Manager แก่บัญชีที่ผ่านการยืนยันตัวตนและเข้าเงื่อนไข ผู้ใช้ที่ยังไม่ได้บทบาทเข้าเมนูจัดกะไม่ได้ การให้สิทธิ์บันทึกผู้ให้สิทธิ์ เวลา และบทบาทที่ให้
2. **บัญชีผู้ใช้** ดูและค้นหาบัญชีเดโม่ พร้อมดูประวัติการกำหนดบทบาทครั้งแรก

ระบบจำกัดบัญชี Admin ตามโปรไฟล์เดโม่ที่กำหนด การมอบสิทธิ์ครั้งแรกเลือกได้สามบทบาทข้างต้น ส่วนการแก้สิทธิ์ระดับสูงของบัญชีที่มีบทบาทแล้วให้ดูข้อค้างด้านท้ายคู่มือ [รายการบัญชีและการให้สิทธิ์](../../apps/api/src/admin-access/admin-access.controller.ts) · [ข้อจำกัดบัญชี Admin เดโม่](../../apps/api/src/admin-access/demo-access.ts)

### HR · 4 เมนูในเครื่อง

1. **ตารางกะรวม** ดูตารางกะที่ประกาศใช้แล้วในขอบเขต A–D
2. **ตารางกะปิดเดือนและ CSV** ในเครื่องที่เปิดฟังก์ชันนี้ ดูและดาวน์โหลดเดือนก่อนที่ประกาศใช้แล้ว ใช้ข้อมูลชุดเดียวกับหน้าตารางปิดเดือน ระบบบันทึกการส่งออกและเวอร์ชันของตาราง หากปิดฟังก์ชันนี้ เมนูจะแสดงข้อมูลสรุปและส่งออก CSV จากเดโม่ในเบราว์เซอร์
3. **ตรวจสอบ OT และประวัติ** ในเครื่องเปิดประวัติที่ API อนุญาตตามขอบเขตของบัญชี HR
4. **แจ้งเตือน** ดูรายการที่ส่งถึงบัญชีตัวเอง

HR ใช้สิทธิ์อ่านและส่งออกตามที่เปิดไว้ ตัวตรวจการเข้าสู่ระบบของฐานกลางเดโม่ยังไม่เปิดให้บัญชี HR [สิทธิ์และข้อมูลส่งออก](../../apps/api/src/schedules/schedules.service.ts) · [ขอบเขต API ประวัติ](../../apps/api/src/audit/audit.controller.ts) · [ขอบเขตเข้าสู่ระบบ](../../apps/api/src/auth/auth.service.ts)

### External / Van Driver · 2 เมนูในเครื่อง

1. **ตารางรับส่งพนักงาน** เปิดหน้าข้อมูลขนส่งสังเคราะห์และกดรับทราบในเดโม่ของเครื่อง
2. **แจ้งเตือน** ดูรายการของบัญชีตัวเอง

สิทธิ์ผู้ใช้ภายนอกจำกัดกับหน้าขนส่งและข้อมูลของบัญชีตัวเอง ฐานกลางเดโม่ยังไม่เปิดเข้าสู่ระบบด้วยบทบาทนี้ [หน้าขนส่ง](../../apps/web/src/features/external/view.js) · [ตัวตรวจสิทธิ์ API](../../apps/api/src/auth/access.guard.ts) · [ขอบเขตเข้าสู่ระบบ](../../apps/api/src/auth/auth.service.ts)

### ผู้ใช้ใหม่ที่รอกำหนดบทบาท · 0 เมนูจัดกะ

บัญชีที่เข้ากติกาแต่ยังไม่ได้บทบาทจะเห็นหน้ารอสิทธิ์และออกจากระบบได้ ระบบใหม่ส่งคิวให้ Admin ตามเงื่อนไขของโหมดเดโม่ บัญชีเข้าสู่ระบบผ่าน Supabase Auth ด้วยอีเมลและรหัสผ่านหรือ Microsoft เมื่อผู้ให้บริการนั้นเปิดใช้ การจับคู่บัญชี Microsoft กับพนักงานมีตัวเลือกเปิดใช้งานแยกและต้องพบอีเมลตรงเพียงบัญชีเดียวที่ยังไม่ผูก [การเข้าสู่ระบบและผูกบัญชี](../../apps/api/src/auth/auth.service.ts) · [หน้ากำหนดสิทธิ์](../../apps/api/src/admin-access/admin-access.controller.ts)

## กฎที่ใช้กับคำขอส่วนกลาง

1. **วันที่ยื่นได้** เลือกวันที่ตั้งแต่วันนี้ถึงวันสุดท้ายของเดือนปัจจุบันตามเวลาไทย ทุกวันที่เกี่ยวข้องต้องอยู่ในกรอบนี้ เดือนย้อนหลังเปิดดูได้ ส่วนหน้าเว็บเปิดการยื่นจากตารางที่ประกาศใช้แล้วตามสิทธิ์ของผู้ดู
2. **เส้นตายอนุมัติ** ต้องกดอนุมัติครบภายใน 24 ชั่วโมงหลังยื่นและก่อนเที่ยงคืนเข้าสู่เดือนถัดไปตามเวลาไทย ใช้เวลาที่มาถึงก่อนเป็นเส้นตายเดียวกันสำหรับผู้อนุมัติทุกคน เช่น ยื่นวันที่ 30 พฤศจิกายน 18:00 น. ครบ 24 ชั่วโมงวันที่ 1 ธันวาคม 18:00 น. ระบบปิดรับการอนุมัติเมื่อเข้าสู่วันที่ 1 ธันวาคม 00:00 น. กติกาปัจจุบันเปิดให้อนุมัติในวันเข้ากะได้แม้กะเริ่มแล้ว ถ้าคำขอยังอยู่ในกรอบเวลาและผ่านเงื่อนไขอื่น
3. **ผลต่อปฏิทิน** ผู้อนุมัติที่ได้รับมอบหมายกดลำดับไหนก็ได้ ตารางเปลี่ยนเมื่อได้รับอนุมัติครบ ระบบตรวจคำขอ ผู้อนุมัติ และข้อมูลกะอีกครั้งก่อนลงตาราง การปฏิเสธต้องมีเหตุผล
4. **ถอนคำขอที่รออนุมัติ** ผู้ยื่นถอนก่อนเส้นตายได้เมื่อผู้อนุมัติทุกคนยังไม่ได้กด ในกรณีสลับกะ API ปัจจุบันเปิดขั้นตอนถอนคำขอรออนุมัติให้ผู้ยื่นบทบาท Employee
5. **ยกเลิกหลังอนุมัติ** ผู้ยื่นกดยกเลิกก่อนเวลาเริ่มกะที่เกี่ยวข้อง กรณีสลับกะยึดเวลาเริ่มงานที่เร็วที่สุดของกะก่อนหรือหลังสลับ กรณีลาใช้กะเดิมที่ขอลา และ OT ใช้กะ OT ที่ขอ ระบบคืนข้อมูลจากกะเดิมที่บันทึกไว้และคืนโควตาเฉพาะสลับกะ หากกะเริ่มแล้ว กะถูกเปลี่ยนต่อ หรือคืนแล้วไม่ผ่านกฎ ระบบปฏิเสธการยกเลิก
6. **คำขอทับกะเดิม** พนักงานหนึ่งคนมีคำขอที่ยังรออนุมัติหรืออนุมัติแล้วและยังมีผลได้หนึ่งรายการต่อวัน ตรวจทุกช่องที่คำขอจะเปลี่ยน รวมถึงคู่สลับ ผู้ทำแทน และวันที่สองของการสลับคนละวัน ต้องยกเลิกคำขอเดิมก่อนยื่นใหม่ หากอนุมัติแล้วต้องคืนกะเดิมสำเร็จด้วย คำขอที่ถูกปฏิเสธ หมดอายุ หรือยกเลิกสำเร็จแล้วเปิดให้ยื่นใหม่ตามเงื่อนไขปกติ

## กฎเฉพาะของคำขอทั้ง 4 ประเภท

### 1. สลับกะข้ามทีม

- **สิทธิ์และคู่สลับ** ผู้ยื่นเลือกกะของตัวเองกับคู่สลับต่างทีมที่มีประเภทพนักงานเดียวกัน กะทั้งคู่ต้องมีผลในตาราง รหัสกะที่นำมาสลับกันต้องทำให้ตารางเปลี่ยน และกะลาถูกกันออกจากการสลับ
- **สลับวันเดียว** จับคู่ช่องกะของสองคนในวันเดียวกัน เช่น M ↔ N หรือ M ↔ O เมื่อผ่านกฎ คนที่รับกะทำงานจากการสลับกับวันหยุดได้รับรหัสกะที่สลับมา เช่น M หรือ N
- **สลับคนละวัน** เลือกสองวันในเดือนเดียวกันกับคู่สลับคนเดิม วันแรกคนหนึ่งทำงานและอีกคนหยุด วันที่สองสลับกันทำงานและหยุด ระบบตรวจและเปลี่ยนทั้งสี่ช่องพร้อมกัน ใช้โควตาหนึ่งครั้งต่อคำขอ
- **อนุมัติ** Employee ส่งให้หัวหน้ากะทั้งสองทีมอนุมัติคนละช่องในลำดับใดก็ได้ หาก Supervisor ยื่น ให้ Manager พิจารณาคนเดียว โควตาถูกใช้หลังอนุมัติครบ

#### Rule Check สลับกะบน Supabase

เมื่อเปิดด้วย `pnpm dev:supabase` และใช้ฟอร์มสลับกะส่วนกลาง หน้าเว็บส่งช่องกะที่เลือกไปให้ API ตรวจด้วยข้อมูลตารางเดโม่ใน Supabase ปุ่มส่งคำขอเปิดเมื่อ API ตอบว่าผ่าน หลังจากนั้น API ตรวจซ้ำตอนยื่นและตอนกดอนุมัติ หากข้อมูลกะเปลี่ยนไปหรือไม่ผ่านกฎในจังหวะนั้น ระบบปฏิเสธการดำเนินการ

**กฎที่บังคับใช้แล้ว**

- **วันทำงานต่อเนื่อง** แสดงช่วงที่ทำงานติดกันยาวสุดในตารางที่ตรวจ แยกผู้ขอและคู่สลับก่อน–หลังสลับ พร้อมวันที่ เช่น ก่อน 4/6 วัน → หลัง 6/6 วัน นับวันก่อนและหลังวันที่แก้ รวมวันข้ามเดือน เมื่อครบ 6 วันจะแจ้งวันที่ต้องหยุด และเมื่อ 7 วันขึ้นไปจะไม่ผ่าน
- **เวลาพักระหว่างกะ** แสดงผลหนึ่งบรรทัดต่อคน พักอย่างน้อย 12 ชั่วโมงจากเวลาเลิกกะก่อนถึงเวลาเริ่มกะถัดไป เช่น กะดึกเลิกวันที่ 16 เวลา 07:30 น. จะลงกะเช้า 07:30 น. ไม่ได้ และลงได้เร็วสุดเวลา 19:30 น. หากผ่านเงื่อนไขอื่น เมื่อไม่ผ่านจะแสดงเวลาเลิก เวลาเริ่ม และเวลาที่ทับกันหรือเวลาพักที่ไม่พอ รวมคู่กะที่ข้ามวันหรือข้ามเดือน
- **เงื่อนไขร่วม** ต้องต่างทีม มีประเภทพนักงานตรงกัน ช่องกะยังมีผลในตารางและไม่มีรหัสลา L กะเดิมต้องต่างกัน ระบบตรวจเจ้าของกะและวันที่ของช่องที่จับคู่ด้วย แม้ซ่อนสองบรรทัดนี้จากหน้าสรุปเมื่อผ่าน สำหรับการสลับคนละวันจะตรวจเพิ่มว่ามีสองวันต่างกันในเดือนเดียวกัน ใช้คู่เดิม และอีกฝ่ายหยุดในวันที่ต้องเข้าทำแทน
- **ช่วงเวลายื่นและอนุมัติ** วันที่สลับเลือกได้ตั้งแต่วันนี้ถึงวันสุดท้ายของเดือนตามเวลาไทย คำขอต้องอนุมัติครบก่อนหมดอายุ 24 ชั่วโมงหรือก่อนเข้าสู่เดือนใหม่ แล้วแต่เวลาใดถึงก่อน
- **โควตา** หน้า Rule Check แสดงจำนวนคงเหลือของผู้ยื่น คำขอรออนุมัติยังไม่ใช้โควตา แม้ยอดคงเหลือเป็นศูนย์ก็ยังยื่นได้ถ้าผ่านเงื่อนไขอื่น ระบบตรวจยอดอีกครั้งก่อนอนุมัติครบและกันการลงตารางเมื่อไม่มีโควตา

**รายการที่ยังขึ้น “รอยืนยัน” ในหน้าตรวจ** ได้แก่ กำลังคนขั้นต่ำ ทักษะเฉพาะงาน และรอบทำงาน 2 วันหยุด 2 วัน รายการที่ขึ้นสถานะนี้ไม่มีผลต่อการส่งหรืออนุมัติคำขอ

**กติกาที่เจ้าของระบบยืนยันแล้ว** โครงสร้างทีมมีหัวหน้ากะ 1 คนและพนักงานกะ 6 คน และไม่มีการบล็อกคำขอตามกำลังคนขั้นต่ำหลังสลับ ให้ใช้บทบาทของคนทั้งคู่ในการตรวจสิทธิ์สลับกะ ส่วนตำแหน่งใช้บันทึกหน้าที่หน้างาน ปัจจุบันฐานกลางยังคัดคู่สลับและตรวจด้วยตำแหน่งตรงกัน จึงยังต้องปรับให้รองรับ Boardman กับ Field Operator ที่มีบทบาทพนักงานกะเหมือนกัน

### 2. ขอลา

- **ฟอร์ม** เลือกกะทำงานของตัวเองในตารางที่ประกาศใช้แล้ว เลือกประเภทลาพักผ่อน (V) ลาป่วย (S) ลากิจ (B) หรือลาอื่น ๆ (VG) ช่อง **เปลี่ยนเป็น** ในผลจำลองแสดงเฉพาะตัวย่อที่เลือก กรอกเหตุผลทุกครั้ง หลังตัดช่องว่างหัวท้ายต้องมีข้อความและยาวไม่เกิน 1,000 ตัวอักษร การลาใน ShiftFlow ใช้ลงปฏิทินและติดตามคำขอ พนักงานยังดำเนินเอกสารลาตามขั้นตอนบริษัท
- **ไม่มีคนแทน** Employee ส่งให้ Supervisor ของทีมตัวเอง เมื่ออนุมัติ กะของผู้ขอเปลี่ยนเป็น L และไม่กระทบตารางคนอื่น
- **มีคนแทน** คู่แทนต้องต่างทีม บทบาทเดียวกัน และมีวันหยุด O ที่มีผลในวันนั้น รองรับการแทนกะ M หรือ N เมื่ออนุมัติครบ ผู้ขอขึ้น L ส่วนผู้ทำแทนขึ้น MT สำหรับกะเช้าหรือ NT สำหรับกะดึก ระบบตรวจวันทำงานต่อเนื่อง เวลาที่ทับซ้อน และเวลาพักอย่างน้อย 12 ชั่วโมงของผู้ทำแทน Employee ส่งให้ Supervisor ของทั้งสองทีมและอนุมัติได้ทั้งสองลำดับ
- **คำขอของหัวหน้ากะ** Manager พิจารณาคนเดียวทั้งแบบมีและไม่มีคนแทน หากต้องมีคนแทนให้เลือกหัวหน้ากะต่างทีมที่ผ่านกฎเดียวกัน
- **รายละเอียดและประวัติ** ผู้ยื่น ผู้ที่มาทำแทน และผู้อนุมัติที่ได้รับมอบหมายอ่านเหตุผลจากคำขอได้ ตารางรวมแสดงรหัส L การกรอกเหตุผลให้ใส่เท่าที่จำเป็นต่อการจัดกะ โดยเฉพาะข้อมูลสุขภาพ รายละเอียดประเภทลา เหตุผลที่ยื่น และเหตุผลปฏิเสธมีอายุเก็บ 12 เดือนนับจากคำขอสิ้นสุดหรือหมดอายุ ผลบนปฏิทินและหลักฐานอนุมัติใช้กติกาการเก็บของตัวเอง
- **ยกเลิก** คืนกะเดิมของผู้ลาและวันหยุดเดิมของผู้ทำแทนเมื่อยังเข้าเงื่อนไขยกเลิก คำขอลาไม่ใช้โควตาสลับกะ

### 3. ขอ OT รายบุคคล

- **ฟอร์ม** หนึ่งคำขอต่อหนึ่งคนต่อหนึ่งวัน ผู้ที่จะทำ OT ยื่นด้วยตัวเองจากวันหยุด O หรือช่อง – ที่เป็นวันไม่ทำงานและยังมีผลในตารางที่ประกาศใช้แล้ว เลือกกะเต็มช่วง MT หรือ NT หากสองคนถูกเรียกมาทำ OT วันเดียวกัน ให้แต่ละคนยื่นแยกกัน
- **Rule Check** เมื่อเลือก MT หรือ NT ฟอร์มตรวจตารางกับ API ก่อนเปิดปุ่มส่ง แสดงวันทำงานติดกันก่อน–หลังและเวลาพักอย่างน้อย 12 ชั่วโมง รวมกะข้ามคืน ถ้าเวลาพักไม่พอจะแจ้งเวลาเลิกกะและเริ่มกะที่เกี่ยวข้อง ตอนส่งและก่อนลงตารางระบบตรวจอีกครั้ง และกันคำขอซ้ำตามกติกาเดิม
- **อนุมัติและยกเลิก** Employee ส่งให้ Supervisor ของทีมตัวเอง หาก Supervisor ยื่น ส่งให้ Manager พิจารณาคนเดียว เมื่ออนุมัติระบบอัปเดตช่องผู้ยื่นเป็น MT หรือ NT หากยกเลิกได้จะคืนรหัสเดิม O หรือ – คำขอนี้ไม่ใช้โควตาสลับกะ

### 4. ขอย้ายวันหยุดนักขัตฤกษ์ · เดโม่ในเบราว์เซอร์

- เลือกวันหยุดเดิมที่ต้องการเข้าทำงานและเลือกวันทำงานอีกวันเพื่อหยุดแทน ตัวเลือกวันเดิมดูจาก O, H หรือเครื่องหมายวันหยุดตามเงื่อนไขของฟอร์ม วันหยุดใหม่ต้องเป็นวันทำงานที่เลือกได้ในเดือนเดียวกันและห่างไม่เกิน 7 วัน
- เลือกทำกะเช้าหรือกะดึกในวันเดิม วันหยุดใหม่แสดง H หากต้นทางเป็น H กรณีอื่นใช้ O ฟอร์มเดโม่มีช่องเหตุผลและตัวเลือกยื่นย้อนหลัง
- เดโม่จัดคิวให้หัวหน้าทีมของ Employee หรือ Manager เมื่อ Supervisor ยื่น การอนุมัติและผลต่อปฏิทินส่วนนี้อยู่ในเบราว์เซอร์

## ตารางกะ โควตา การปิดเดือน และประวัติ

- **รอบกะ A–D** ตารางเดโม่อิงวันที่ 1 สิงหาคม 2569 เป็นจุดอ้างอิง วันนั้น Shift B เข้ากะดึกและ Shift D เข้ากะเช้า ส่วน A กับ C หยุด ทุกรอบเดินตามรูปแบบ **เช้า 2 วัน → หยุด 2 วัน → ดึก 2 วัน → หยุด 2 วัน** ตามลำดับวันที่จริงข้ามเดือน แต่ละวันของรอบพื้นฐานมีหนึ่งทีมเช้า หนึ่งทีมดึก และสองทีมหยุด ข้อมูลกะเฉพาะคนที่บันทึกไว้มีผลเหนือตารางพื้นฐาน ในเครื่องเดือนที่ไม่มีข้อมูลอาจเห็นตารางคาดการณ์ ส่วนฐานกลางแสดงสถานะยังไม่มีตารางของเดือนนั้น [รอบกะ](../../apps/web/src/shared/scheduling/rotation.json) · [การปรับข้อมูลเดโม่](../../apps/api/migrations/013_align_demo_roster_to_august.sql) · [การแสดงเดือนที่ยังไม่มีข้อมูล](../../apps/web/src/features/schedule/page.js)
- **ทีมตามวันที่มีผล** ตารางใช้ทีมของพนักงานตามวันที่ที่เปิดดู เช่น ย้ายจาก A ไป B มีผลวันที่ 16 ช่วงวันที่ 1–15 ยังอ้างอิงทีม A วันที่ 16 เป็นต้นไปอ้างอิงทีม B กะที่บันทึกไว้ในตารางประกาศแล้วคงตามข้อมูลเดิมและต้องจัดการแยกเมื่อจำเป็น คำขอที่ขัดกับการย้ายต้องจัดการให้เสร็จก่อนบันทึก [ตรรกะการย้ายทีม](../../apps/api/src/people-management/people-management.service.ts)
- **โควตาสลับกะ** ค่าเริ่มต้นฝั่ง API คือ 2 ครั้งต่อคนต่อเดือน หากมีค่ากำหนดสำหรับเดือนนั้นให้ใช้ค่าที่กำหนด นับเฉพาะรายการที่อนุมัติครบและนับให้ผู้ยื่นคนเดียว ยกเลิกหลังอนุมัติสำเร็จจะคืนรายการใช้โควตาเดิมหนึ่งครั้ง Manager กำหนดจำนวนเต็มบวกสำหรับเดือนถัดไป ค่ามีผลตั้งแต่วันที่ 1 ตามเวลาไทย หน้าจอเดโม่ที่อ่านจากเบราว์เซอร์อย่างเดียวมีค่าเริ่มต้น 1 ครั้ง [โควตา API](../../apps/api/src/requests/swap-quota.service.ts) · [ค่าเริ่มต้นเดโม่ในเบราว์เซอร์](../../apps/web/src/app/state.js)
- **ปิดเดือนและ CSV** HR ในเครื่องที่เปิดสิทธิ์ส่งออกเดือนที่ประกาศใช้แล้วและปิดไปแล้ว ค่าเริ่มต้นเป็นเดือนก่อน CSV ใช้รหัสพนักงาน ทีม วันที่ และรหัสกะ รองรับการเปิดใน Excel และป้องกันข้อมูลถูกตีความเป็นสูตร ระบบเก็บผู้ส่งออก เวลา เดือน และเวอร์ชันตาราง [การปิดเดือนและส่งออก](../../apps/api/src/schedules/schedules.service.ts) · [แผนปิดเดือน](2026-11-10-hr-month-close-plan.md)
- **ประวัติและแจ้งเตือน** ประวัติส่วนตัวเลือกเฉพาะเหตุการณ์จากคำขอที่เกี่ยวข้องและแสดงล่าสุดสูงสุด 100 รายการ การแจ้งเตือนส่วนกลางแสดงล่าสุด 30 รายการสำหรับผู้รับ สิทธิ์อ่านรายละเอียดคำขอยังตรวจเมื่อเปิดจากประวัติ สถานะอ่านแล้วในเดโม่เก็บในเบราว์เซอร์ [API ประวัติ](../../apps/api/src/audit/audit.controller.ts) · [API แจ้งเตือน](../../apps/api/src/notifications/notifications.controller.ts) · [สถานะอ่านแล้ว](../../apps/web/src/features/notifications/store.js)
- **หลักฐานการอนุมัติ** ระบบบันทึกผู้ทำรายการ เวลา คำขอ และกะหรือเวอร์ชันที่เกี่ยวข้อง การเปลี่ยนตารางจากการอนุมัติครั้งสุดท้ายกับหลักฐานใช้ธุรกรรมเดียวกัน การตั้งค่า API กำหนดขั้นต่ำสำหรับระยะเก็บบันทึกตรวจสอบไว้ 90 วันตามเอกสารโครงการ [การบันทึกคำขอ](../../apps/api/src/requests/requests.service.ts) · [การตั้งค่า API](../../apps/api/src/config.ts) · [หลักเกณฑ์ข้อมูลและบันทึกตรวจสอบ](../01-requirements/rule.md)

## เงื่อนไขที่ยังต้องยืนยันก่อนใช้จริง

- **Rule Check สลับกะ** ยังรอยืนยันว่าจะบังคับรักษารอบทำงาน 2 วันหยุด 2 วันหลังสลับหรือใช้เป็นรอบตั้งต้นของตาราง ตัวเลขในหน้าภาพรวมกำลังพลใช้ดูจำนวนคนในตาราง
- **คำขอข้ามประเภท** ฐานกลางตรวจช่องกะของสลับกะ ลา และ OT ร่วมกัน การย้ายวันหยุดนักขัตฤกษ์ตรวจช่องเดิมและช่องใหม่ด้วยกติกาเดียวกันในเดโม่บนเบราว์เซอร์ การให้ MT หรือ NT กับผู้รับกะจากวันหยุดมีในคำขอลาแบบมีผู้ทำแทนและคำขอ OT ส่วนคำขอสลับกะใช้รหัสกะที่สลับมา
- **เวลาของคำขอลา** ระหว่างทบทวนกติกาเคยมีเงื่อนไขให้อนุมัติก่อนกะเริ่ม ปัจจุบันโค้ดใช้กรอบ 24 ชั่วโมงและสิ้นเดือนร่วมกับสลับกะ เงื่อนไขก่อนเริ่มกะใช้กับการยกเลิกหลังอนุมัติ หากต้องการใช้เงื่อนไขก่อนเริ่มกะตอนอนุมัติด้วย ต้องยืนยันกติกากลางก่อนแก้
- **ช่องว่างระหว่างหน้าเว็บกับ API** หน้าเว็บใช้สถานะประกาศใช้ในการเปิดฟอร์ม ส่วน API ตรวจสถานะนี้โดยตรงสำหรับลาและ OT เส้นทางสลับกะตรวจช่วงวันที่ ความพร้อมของช่องกะและสิทธิ์เขียนตาราง
- **การย้ายวันหยุดนักขัตฤกษ์** ยังต้องกำหนดกติกาการลงฐานกลาง การอนุมัติ วันย้อนหลัง และการคืนกะหลังยกเลิกให้ครบสำหรับการใช้ร่วมกัน
- **สิทธิ์บัญชีและข้อมูลจริง** ยังขาดหน้าจอจัดการการให้และถอนสิทธิ์ระดับ Manager/Admin สำหรับบัญชีทั่วไป ต้องตรวจขอบเขตการเปิดตารางทั้ง A–D ในเดโม่กับสิทธิ์ตามทีมของข้อมูลจริง และตรวจการเก็บกับการป้องกันบันทึกตามข้อกำหนดก่อนใช้จริง HR และผู้ขับรถยังอยู่ในโหมดเดโม่ในเครื่อง

# บันทึกตรวจความพร้อม: Admin และ Manager

วันที่: 2026-10-30

สถานะ: ตรวจโครงสร้างเดิมแล้ว; ยังไม่ใช่ข้อกำหนดที่อนุมัติให้สร้างระบบจัดสิทธิ์

## ข้อตกลงจากเจ้าของโปรเจค

- แยก Admin ซึ่งจัดการสิทธิ์เข้าใช้ระบบ ออกจาก Manager ซึ่งรับผิดชอบข้อมูลด้านงาน
- แนวทางรับผู้ใช้ใหม่: Manager ยืนยันตัวพนักงานและทีม; Admin ผูกบัญชีและให้สิทธิ์ตามกติกาที่จะตกลง
- การผูกบัญชี Microsoft อัตโนมัติยังไม่เปิดใช้
- ทำทีละขั้นและอธิบายผลให้เจ้าของเข้าใจ
- เจ้าของขอเลื่อนการตัดสินใจเรื่องผู้มีอำนาจแต่งตั้ง/ถอนสิทธิ์ Admin และ Manager ไปคุยภายหลัง
- การเลื่อนคำถามไม่ถือเป็นการอนุญาตให้เลือกกติกาใดแทนเจ้าของ

## สิ่งที่ตรวจพบจากโค้ด

1. `apps/api/migrations/001_core.sql`: `users.role_id` รองรับหนึ่ง Role ต่อผู้ใช้; `employee_id` ผูกแบบไม่ซ้ำ จึงต้องออกแบบก่อนรองรับหลาย Role ในบัญชีเดียว
2. `apps/api/migrations/002_demo_profiles.sql`: เงื่อนไขบัญชีที่ไม่มี employee รองรับเฉพาะ Manager/External เดโม่ ยังไม่รองรับ Admin
3. `apps/api/src/auth/auth.service.ts`: ตรวจตัวตนจาก Auth แล้วค้นหาบัญชีที่ผูกไว้; ผู้ไม่ถูกผูกยังได้ `ACCOUNT_NOT_LINKED` ไม่ได้มีคิวรออนุมัติในฐานข้อมูล
4. `apps/api/src/auth/access.guard.ts`: API ปัจจุบันเรียก resolve เพื่อบังคับบัญชีที่ผูกแล้ว การสร้างทางเข้าของผู้รออนุมัติต้องกำหนดขอบเขตข้อมูลเฉพาะอย่างชัดเจน
5. `apps/web/src/app/profiles.js`: Role ที่ไม่รู้จักถูกแสดงเป็นผู้ใช้ภายนอก ต้องเพิ่มการรองรับ Admin อย่างชัดเจนก่อนใช้งาน
6. `apps/web/src/app/session.js`: ผู้ใช้ที่ไม่ใช่ External จะโหลดข้อมูลตาราง ต้องกำหนดเส้นทางโหลดข้อมูลสำหรับ Admin ตามสิทธิ์ที่อนุมัติ
7. `apps/web/src/features/manager/people.js`: การเพิ่ม/แก้พนักงานยังเก็บในเบราว์เซอร์; ไม่สามารถใช้เป็นหลักฐานยืนยันพนักงานส่วนกลางได้
8. `apps/api/src/employees/employees.controller.ts`: การอ่านรายชื่อพนักงานปัจจุบันยังไม่อนุญาต Manager ต้องตกลงขอบเขตก่อนเพิ่มสิทธิ์
9. `apps/api/migrations/001_core.sql`: `audit_logs.user_id` อ้างถึงผู้ใช้ในระบบ จึงต้องออกแบบการระบุตัวผู้ขอเข้าใช้ที่ยังไม่ได้ผูกบัญชี ก่อนบันทึกเหตุการณ์คิวรออนุมัติ

## งานถัดไปที่ทำได้โดยยังไม่เลือกนโยบายแทนเจ้าของ

- ใช้รายการจุดกระทบข้างต้นวางแผนการเปลี่ยนแปลงและกรณีทดสอบ
- แยกข้อกำหนดที่ตกลงแล้วออกจากคำถามค้างในร่างที่จะจัดทำภายหลัง
- รักษาการทำงานของ Login และบัญชีเดโม่เดิมระหว่างออกแบบ
- ก่อนสร้างฟีเจอร์ข้อมูลพนักงาน ให้กำหนดวัตถุประสงค์ ข้อมูลขั้นต่ำ ผู้มีสิทธิ์ อายุจัดเก็บ เหตุการณ์ตรวจสอบ และอำนาจอนุมัติตาม `rule.md`

## คำถามค้างก่อนทำส่วนที่เกี่ยวข้อง

- ใครอนุมัติแต่งตั้ง/ถอนสิทธิ์ Admin และ Manager: เจ้าของอนุมัติแล้ว Admin ดำเนินการ (ควบคุมชัดแต่เพิ่มขั้นตอน), Admin ตัดสินใจเอง (รวดเร็วแต่อำนาจสูง), หรือ Admin สองคนร่วมอนุมัติ (ตรวจสอบกันแต่ต้องมีสองคน)
- ใครเป็น Admin คนแรก และยืนยันตัวตน/แต่งตั้งด้วยกระบวนการใด
- Manager ดูแลทีมใด และข้อกำหนดเดิมเรื่อง Supervisor จัดการข้อมูลพนักงานจะอยู่ร่วมกับหน้าที่ Manager อย่างไร
- อนุญาตหลาย Role ชุดใดบ้าง และคนถือหลาย Role อนุมัติรายการที่ตนเสนอได้หรือไม่
- อายุจัดเก็บคำขอที่รอ/ถูกปฏิเสธ ข้อมูลบัญชีที่ปิด และหลักฐานการให้สิทธิ์คือเท่าใด; ขั้นต่ำ 90 วันของ log ตามกติกาโปรเจคไม่ใช่อายุจัดเก็บของข้อมูลทุกประเภท
- ข้อมูลขั้นต่ำที่ใช้ยืนยันพนักงาน ผู้มีสิทธิ์อ่านประวัติ และวิธีระงับ/คืนสิทธิ์ต้องกำหนดก่อนสร้าง

# บันทึกตรวจความพร้อม: Admin และ Manager

วันที่: 2026-10-30

สถานะ: ตรวจโครงสร้างเดิมแล้ว; ยังไม่ใช่ข้อกำหนดที่อนุมัติให้สร้างระบบจัดสิทธิ์

## ข้อตกลงจากเจ้าของโปรเจค

- แยก Admin ซึ่งจัดการสิทธิ์เข้าใช้ระบบ ออกจาก Manager ซึ่งรับผิดชอบข้อมูลด้านงาน
- แนวทางรับผู้ใช้ใหม่: Manager ยืนยันตัวพนักงานและทีม; Admin ผูกบัญชีและให้สิทธิ์ตามกติกาที่จะตกลง
- การผูกบัญชี Microsoft อัตโนมัติยังไม่เปิดใช้
- ทำทีละขั้นและอธิบายผลให้เจ้าของเข้าใจ
- เจ้าของขอเลื่อนการตัดสินใจเรื่องผู้มีอำนาจแต่งตั้ง/ถอนสิทธิ์ Admin และ Manager ไปคุยภายหลัง
- การเลื่อนคำถามไม่ถือเป็นการอนุญาตให้เลือกกติกาใดแทนเจ้าของ

## สิ่งที่ตรวจพบจากโค้ด

1. `apps/api/migrations/001_core.sql`: `users.role_id` รองรับหนึ่ง Role ต่อผู้ใช้; `employee_id` ผูกแบบไม่ซ้ำ จึงต้องออกแบบก่อนรองรับหลาย Role ในบัญชีเดียว
2. `apps/api/migrations/002_demo_profiles.sql`: เงื่อนไขบัญชีที่ไม่มี employee รองรับเฉพาะ Manager/External เดโม่ ยังไม่รองรับ Admin
3. `apps/api/src/auth/auth.service.ts`: ตรวจตัวตนจาก Auth แล้วค้นหาบัญชีที่ผูกไว้; ผู้ไม่ถูกผูกยังได้ `ACCOUNT_NOT_LINKED` ไม่ได้มีคิวรออนุมัติในฐานข้อมูล
4. `apps/api/src/auth/access.guard.ts`: API ปัจจุบันเรียก resolve เพื่อบังคับบัญชีที่ผูกแล้ว การสร้างทางเข้าของผู้รออนุมัติต้องกำหนดขอบเขตข้อมูลเฉพาะอย่างชัดเจน
5. `apps/web/src/app/profiles.js`: Role ที่ไม่รู้จักถูกแสดงเป็นผู้ใช้ภายนอก ต้องเพิ่มการรองรับ Admin อย่างชัดเจนก่อนใช้งาน
6. `apps/web/src/app/session.js`: ผู้ใช้ที่ไม่ใช่ External จะโหลดข้อมูลตาราง ต้องกำหนดเส้นทางโหลดข้อมูลสำหรับ Admin ตามสิทธิ์ที่อนุมัติ
7. `apps/web/src/features/manager/people.js`: การเพิ่ม/แก้พนักงานยังเก็บในเบราว์เซอร์; ไม่สามารถใช้เป็นหลักฐานยืนยันพนักงานส่วนกลางได้
8. `apps/api/src/employees/employees.controller.ts`: การอ่านรายชื่อพนักงานปัจจุบันยังไม่อนุญาต Manager ต้องตกลงขอบเขตก่อนเพิ่มสิทธิ์
9. `apps/api/migrations/001_core.sql`: `audit_logs.user_id` อ้างถึงผู้ใช้ในระบบ จึงต้องออกแบบการระบุตัวผู้ขอเข้าใช้ที่ยังไม่ได้ผูกบัญชี ก่อนบันทึกเหตุการณ์คิวรออนุมัติ

## งานถัดไปที่ทำได้โดยยังไม่เลือกนโยบายแทนเจ้าของ

- ใช้รายการจุดกระทบข้างต้นวางแผนการเปลี่ยนแปลงและกรณีทดสอบ
- แยกข้อกำหนดที่ตกลงแล้วออกจากคำถามค้างในร่างที่จะจัดทำภายหลัง
- รักษาการทำงานของ Login และบัญชีเดโม่เดิมระหว่างออกแบบ
- ก่อนสร้างฟีเจอร์ข้อมูลพนักงาน ให้กำหนดวัตถุประสงค์ ข้อมูลขั้นต่ำ ผู้มีสิทธิ์ อายุจัดเก็บ เหตุการณ์ตรวจสอบ และอำนาจอนุมัติตาม `rule.md`

## คำถามค้างก่อนทำส่วนที่เกี่ยวข้อง

- ใครอนุมัติแต่งตั้ง/ถอนสิทธิ์ Admin และ Manager: เจ้าของอนุมัติแล้ว Admin ดำเนินการ (ควบคุมชัดแต่เพิ่มขั้นตอน), Admin ตัดสินใจเอง (รวดเร็วแต่อำนาจสูง), หรือ Admin สองคนร่วมอนุมัติ (ตรวจสอบกันแต่ต้องมีสองคน)
- ใครเป็น Admin คนแรก และยืนยันตัวตน/แต่งตั้งด้วยกระบวนการใด
- Manager ดูแลครบ Shift A–D ตามคำยืนยันวันที่ 12 พฤศจิกายน 2569 ส่วนข้อกำหนดเดิมเรื่อง Supervisor จัดการข้อมูลพนักงานยังรอทบทวนร่วมกับหน้าที่ Manager
- อนุญาตหลาย Role ชุดใดบ้าง และคนถือหลาย Role อนุมัติรายการที่ตนเสนอได้หรือไม่
- อายุจัดเก็บคำขอที่รอ/ถูกปฏิเสธ ข้อมูลบัญชีที่ปิด และหลักฐานการให้สิทธิ์คือเท่าใด; ขั้นต่ำ 90 วันของ log ตามกติกาโปรเจคไม่ใช่อายุจัดเก็บของข้อมูลทุกประเภท
- ข้อมูลขั้นต่ำที่ใช้ยืนยันพนักงาน ผู้มีสิทธิ์อ่านประวัติ และวิธีระงับ/คืนสิทธิ์ต้องกำหนดก่อนสร้าง

### ขอบเขตที่เจ้าของยืนยันแล้ว

- ผู้ใช้ที่ยืนยันตัวตนแล้วแต่ยังไม่มีบทบาทต้องรอ Admin กำหนดบทบาทเริ่มต้นเป็น Manager, Supervisor หรือ Employee ก่อนใช้ระบบจัดกะ
- Manager รับช่วงดูแลพนักงานกะและหัวหน้ากะทุกคนใน Shift A–D ทั้งย้ายทีม เปลี่ยนตำแหน่ง และเปลี่ยนบทบาทระหว่าง Employee กับ Supervisor ได้โดยตรง ขอบเขตนี้ไม่ต้องผูก Manager กับทีมใดทีมหนึ่ง การให้หรือถอนสิทธิ์ระดับ Manager และ Admin อยู่ที่ Admin ตามขั้นตอนที่เจ้าของจะยืนยัน
- การย้ายทีมมีวันที่เริ่มใช้ทีมใหม่ ตัวอย่างการย้ายจาก Shift A ไป Shift B วันที่ 16 ต้องแสดงวันที่ 1–15 ตาม Shift A และเก็บประวัติการสลับกะ การลา และรายการเดิม ตั้งแต่วันที่ 16 ให้จัดตารางตาม Shift B โดยแยกการบันทึกการย้ายทีมจากขั้นตอนปรับตารางที่ประกาศแล้ว
- ก่อนบันทึกย้ายทีม ให้ตรวจคำขอที่ยังรอและผลอนุมัติเดิมที่อาจชนกับตารางใหม่ตั้งแต่วันที่มีผล ถ้าพบรายการที่ต้องเคลียร์ ให้แสดงวันและสถานะของรายการแก่ผู้มีสิทธิ์ พักการย้ายจนเคลียร์ และตรวจซ้ำก่อนบันทึก ระบบไม่ยกเลิกหรือย้อนผลอนุมัติอัตโนมัติ
- อ้างอิง [Business Rules ข้อ 3–4](../01-requirements/01-spec/2026-11-04-01-business-rules-master.md#4-login-และการรับผู้ใช้ใหม่) และ [กติกาการใช้ข้อมูลและบันทึกเหตุการณ์](../01-requirements/rule.md)

### ลำดับงานและเงื่อนไขก่อนลงโค้ด

1. **รักษาทีมตามวันที่ของตารางกะ** — วันที่มีผลย้ายทีมเป็นเส้นแบ่งของทีมเดิมและทีมใหม่ ปัจจุบันตารางปิดเดือนและ CSV อ่านทีมจากข้อมูลพนักงานปัจจุบัน ให้ทดสอบว่าก่อนวันย้ายยังเห็นทีมเดิม รวมถึงข้อมูลใน CSV เดือนที่ปิดแล้ว และการจัดกะตามทีมใหม่เริ่มตั้งแต่วันที่มีผล ทดสอบว่าคำขอค้างที่กระทบหรือผลอนุมัติที่ชนกันบล็อกการย้ายโดยไม่เขียนข้อมูลทีม และลองย้ายใหม่ได้หลังเคลียร์แล้ว
2. **จัดการคนผ่าน Backend** — ให้ Manager จัดการพนักงานกะและหัวหน้ากะได้ครบ Shift A–D ตรวจบทบาทของผู้ดำเนินการและผู้ถูกเปลี่ยนก่อนเขียน และปฏิเสธการให้สิทธิ์ระดับ Manager หรือ Admin ผ่านช่องทางนี้ ทดสอบการบันทึกการเปลี่ยนกับหลักฐานในรายการเดียวกัน รวมถึงกรณีหัวหน้าคนเดิมยังมีคำขอสลับกะรออนุมัติ ผู้อนุมัติของคำขอเดิมถูกเก็บตามบัญชีที่ได้รับมอบหมายตอนยื่น จึงต้องยืนยันว่าจะจัดการงานค้างอย่างไรเมื่อคนย้ายทีมหรือเปลี่ยนบทบาท
3. **รับผู้ใช้ใหม่และให้สิทธิ์ครั้งแรก** — กำหนด Admin คนแรก ขั้นตอนยืนยันตัวพนักงาน และข้อมูลที่ Admin จำเป็นต้องใช้ ก่อนสร้างคิวรอหรือเปลี่ยนเส้นทางของ `ACCOUNT_NOT_LINKED` ทดสอบว่าบัญชีที่ยังไม่ได้รับสิทธิ์เข้าถึงข้อมูลจัดกะไม่ได้ และสิทธิ์มีผลเมื่อ Admin ดำเนินการสำเร็จ
4. **ทบทวนการให้และถอนสิทธิ์ระดับสูง** — รอข้อสรุปเรื่องผู้อนุมัติ การถือหลายบทบาท การระงับและคืนสิทธิ์ รวมถึงวิธีรักษาหลักฐานเมื่อเปลี่ยนสิทธิ์ของคนที่มีรายการค้าง

### เกณฑ์ตรวจสำหรับงานย้ายทีมและคำขอส่วนกลาง

- ใช้รหัสพนักงานเดิมตลอดการย้าย และอ่านทีมตามวันที่ของช่องตาราง ทดสอบการย้ายวันที่ 16 โดยตรวจทั้งวันที่ 15 และ 16 ในเดือนเดียวกัน รวมถึงเปิดตารางกับดาวน์โหลด CSV เดือนปิดแล้วก่อนและหลังย้าย ผลของเดือนปิดต้องตรงกัน
- แยกวันที่สังกัดทีมมีผลจากการปรับกะที่ประกาศแล้ว ตรวจคำขอค้างและผลอนุมัติที่ชนกันก่อนบันทึก การเปลี่ยนทีมต้องเก็บผู้ดำเนินการ ทีมเดิม ทีมใหม่ และวันที่มีผลตามกติกาใน `rule.md` ประวัติที่ข้อมูลทีมเดิมไม่ครบต้องตรวจแหล่งข้อมูลก่อนย้ายมาใช้
- เส้นทางยกเลิกสลับกะที่อนุมัติแล้วในกรณีปกติ ทดสอบคืนกะและสิทธิ์พร้อมกัน คืนได้ครั้งเดียว คงหลักฐานเดิม ปฏิเสธเมื่อถึงเวลาเริ่มหรือเมื่อมีการเปลี่ยนตารางภายหลังที่ทำให้คืนค่าไม่ได้
- คำลาจะต่อเข้าฐานกลางด้วยฟอร์มที่ระบุผู้ทำแทน เก็บค่าเดิมของช่องที่กระทบก่อนใช้ผลอนุมัติ เมื่อคนแทนมาจากวันหยุดให้ขึ้น `MT` หรือ `NT` ตามกะที่รับแทน เจ้าของขอเปิดคำถามเรื่องสายอนุมัติคนแทนและอายุใบลาไว้ก่อน โดยมีทางเลือกให้หัวหน้ากะสองทีมอนุมัติครบกรณีต่างทีม ดู [Business Rules หมวด 8](../01-requirements/01-spec/2026-11-04-01-business-rules-master.md#8-ลา-ot-วันหยุด-hr-และขนส่ง--งานแยกที่ยังไม่ให้ใช้โค้ดเดโม่ตัดสินกฎ)

### รอบพัฒนาบนฐานเดโม่

1. ผูกบัญชี Auth ที่ใช้ทดสอบกับโปรไฟล์พนักงานสมมติที่เตรียมไว้ เมื่อบัญชีผ่านการยืนยันตัวตนครั้งแรกจึงเข้าคิวรอ Admin บัญชีที่ไม่มีโปรไฟล์ทดสอบที่ผูกไว้ยังใช้ขั้นตอนเดิม
2. ให้ Admin เดโม่เลือกบทบาทเริ่มต้นจาก Manager, Supervisor หรือ Employee บันทึกผู้ดำเนินการและผลการเปลี่ยนสิทธิ์พร้อมกัน ทดสอบการเปิดคิวด้วยบัญชีอื่นและการส่งกำหนดสิทธิ์ซ้ำ
3. ให้ Manager เดโม่บันทึกการย้ายทีม ตำแหน่ง และบทบาท Employee หรือ Supervisor ผ่าน Backend ใช้เฉพาะชื่อ รหัสพนักงาน ทีม ตำแหน่ง บทบาท และวันที่ที่จำเป็นต่อการทดลอง ใช้การบันทึกหลักฐานตามค่าคงไว้ของฐานเดโม่
4. ตรวจระบบด้วยฐานสังเคราะห์แยก ทั้งเส้นทางอนุมัติเดิม ตารางเดือนปิด การโหลดบทบาทหลัง Admin กำหนด และการอ่านทีมก่อนกับหลังวันย้าย นโยบายเปิดให้บัญชีบริษัทและการแต่งตั้งหรือถอน Admin ระดับบริษัทยังรอข้อสรุปเดิม

### ข้อมูลและหลักฐานที่ต้องยืนยันก่อนเปิดใช้

- วัตถุประสงค์ของรายการข้อมูลคือระบุบัญชี พนักงาน ทีม และบทบาทเพื่อควบคุมการเข้าถึงระบบจัดกะ รายการฟิลด์ขั้นต่ำและผู้มีสิทธิ์อ่านคิวหรือประวัติรอเจ้าของยืนยัน
- การตรวจต้องแยกบทบาทของบัญชีใน `users.role_id` จากตำแหน่งใน `employees.position` เนื่องจากระบบเลือกเส้นทางอนุมัติจากบทบาทและตรวจคุณสมบัติการสลับจากตำแหน่ง ต้องยืนยันว่าการเปลี่ยนมีผลต่อสองข้อมูลและงานที่ค้างอยู่อย่างไร
- บันทึกการปฏิเสธสิทธิ์และการเปลี่ยนสิทธิ์ต้องระบุผู้ดำเนินการ บัญชีที่ได้รับผล เวลา และค่าเดิมกับค่าใหม่ตามเหตุการณ์ โดยใช้หลักฐานที่ได้รับการป้องกัน เกณฑ์เก็บ access log ขั้นต่ำ 90 วันมาจาก `rule.md` ส่วนอายุของคิวและข้อมูลบัญชีรอการตัดสินใจแยกกัน
- ผู้ยื่นคำขอสลับกะส่วนกลางในเครื่องสามารถยกเลิกหลังอนุมัติได้ก่อนกะแรกเริ่ม เมื่อคืนได้ทั้งตารางและโควตาจะกลับพร้อมกัน โดยคงหลักฐานเดิม กฎคืนตารางและค่าที่คำขอเปลี่ยนใช้กับทั้งสลับกะ ลา OT และย้ายวันหยุดนักขัตฤกษ์ตาม [Business Rules หมวด 6](../01-requirements/01-spec/2026-11-04-01-business-rules-master.md#6-การอนุมัติ-สถานะ-และการยกเลิก) วิธีจัดการคำขอที่เปลี่ยนช่องกะต่อเป็นคำถามเปิด

### ผลตรวจระบบเดิม

ทดสอบ API บนฐาน PostgreSQL สังเคราะห์ผ่าน 5 รายการ ครอบคลุมบัญชีที่ยังไม่ผูก การผูก Microsoft แบบเปิดใช้โดยตั้งค่า การป้องกันหลักฐาน และสายอนุมัติของพนักงานกับหัวหน้ากะ การตรวจนี้ใช้ระบบยืนยันตัวตนจำลองของชุดทดสอบ

### ผลทดสอบ Milestone 4 บนฐานเดโม่

- `pnpm test` ผ่าน 55 รายการ เปิดการทดสอบ Chromium สำหรับ Admin, Manager, สลับกะ และ CSV ของ HR บัญชีทดสอบใช้ตัวจำลองเซสชัน Supabase
- Admin เดโม่ให้บทบาทครั้งแรกแก่บัญชีเดโม่ที่ผูกไว้และเข้าสู่ระบบแล้ว บัญชีที่รอสิทธิ์และบัญชีที่ยังไม่ผูกเปิดตารางกะไม่ได้
- Manager เดโม่แก้บทบาทและตำแหน่งได้ การย้ายทีมเปลี่ยนการสังกัดตามวันที่ เก็บตารางปิดเดือน และพักรายการที่มีคำขอค้างหรือผลอนุมัติในอนาคตที่ต้องตรวจ โดยรองรับการย้ายที่ตั้งไว้ล่วงหน้าครั้งละหนึ่งรายการต่อคน

# เอกสารหลัก: กฎและการทำงานของระบบจัดกะ TNC

อัปเดต: **9 พฤศจิกายน 2569 (2026-11-09)**

สถานะ: **ฉบับตรวจความเข้าใจร่วมกัน ก่อนลงโค้ดรอบถัดไป**

เจ้าของขอให้รวม Logic, Business Rules, ข้อสงสัย และ Checklist ในไฟล์เดียว เพื่อลดการอ้างกฎคนละชุด ใช้ไฟล์นี้เป็นจุดอ่านและแก้ความเข้าใจร่วมกันกับ Manager เอกสารเดิมยังเป็นหลักฐานที่มา ไม่ต้องไล่แก้กฎซ้ำหลายไฟล์

**เอกสารนี้ไม่แปลว่า Manager อนุมัติแล้ว หรือระบบทำตามทุกข้อแล้ว** บทบัญญัติใน `rule.md` ยังคงเป็นฐานขั้นต่ำ กฎที่ขัดกันหรือยังไม่ตอบต้องคงสถานะรอคำตอบ ห้ามผู้พัฒนาเลือกแทน

**ทางอ่านสั้นสำหรับประชุม:** เริ่ม [ภาพรวม](#2-ภาพรวมระบบและขอบเขตงาน) → [กฎสลับกะล่าสุด](#5-กฎสลับกะล่าสุด--เจ้าของยืนยันแล้ว) → [คำถามค้าง](#10-คำถามค้าง--ตอบในไฟล์นี้ทีละข้อ) → [บันทึกผลทบทวน](#13-บันทึกการทบทวนร่วมกัน) ส่วนหมวดอื่นใช้เปิดประกอบเมื่อคุยเรื่องนั้น

## 1. วิธีใช้ Checklist

- `[x] เจ้าของยืนยัน` = เจ้าของเลือกหรือยืนยันในแชตแล้ว
- `[ ] Manager ทบทวน` = รอ Manager อ่านและยืนยันไความเข้าใจ/แก้ไข
- `[ ] ตรวจระบบ` = ยังไม่ได้ยืนยันว่าโค้ดทั้งเส้นทางทำตามกฎนั้นผ่านแล้ว
- **ฐานเดิม** = มาจากเอกสารหรือเดโม่เดิม ยังไม่ใช่ข้อยืนยันใหม่ของ Manager
- **รอคำตอบ** = ห้ามตีความเป็นกฎที่ตกลงแล้ว

ทำทีละข้อ: อ่านตัวอย่าง → ตอบ/แก้ข้อความ → Manager ทำเครื่องหมาย → ผู้พัฒนาแก้ตาม → ทดสอบ → จึงทำเครื่องหมายตรวจระบบ อย่าใช้ช่องยืนยันกฎแทนช่องทดสอบโค้ด

## 3. Role และอำนาจ — อ่านแยกจากชื่อเมนู

| Role | หน้าที่/ทิศทางที่มีอยู่ | สิ่งที่ยังต้องเช็ค |
| --- | --- | --- |
| พนักงาน (EMPLOYEE) | ดูตาราง/คำขอที่มีสิทธิ์ ยื่นสลับกับพนักงานต่างทีม | [ ] ขอบเขตข้อมูลของทีมอื่นและการยินยอมของคู่สลับ |
| หัวหน้ากะ (SUPERVISOR) | ตรวจคำขอที่ได้รับมอบหมาย; ยื่นสลับกับหัวหน้าต่างทีมได้ตามกฎใหม่ | [ ] โค้ด Backend ยังต้องขยายสิทธิ์ผู้ยื่น |
| ผู้จัดการ (MANAGER) | อนุมัติคำขอของหัวหน้ากะหนึ่งคน และจัดการพนักงานกะกับหัวหน้ากะได้ครบ Shift A–D ทั้งย้ายทีม เปลี่ยนตำแหน่ง และเปลี่ยนบทบาทระหว่าง Employee กับ Supervisor | [ ] บังคับขอบเขตสิทธิ์ที่ Backend และกำหนดวันที่มีผลกับตารางกะ |
| Admin | กำหนด Role ครั้งแรกก่อนเปิดสิทธิ์ใช้งาน และจัดการการให้หรือถอน Role Manager กับ Admin | [ ] กำหนด Admin คนแรกและขั้นอนุมัติภายในของ Role ระดับสูง |
| HR | ฐานเดิมให้อ่านตารางที่เผยแพร่แล้วและเตรียมข้อมูลส่งออก | [ ] ฟิลด์ รูปแบบ ปลายทาง และหลักฐานการส่งออกที่อนุญาต |
| ผู้ใช้ภายนอก/คนขับรถ | ฐานเดิมให้ดูเฉพาะข้อมูลขนส่งที่จำเป็นแบบอ่านอย่างเดียว | [ ] หน้าขนส่งปัจจุบันเป็นตัวอย่าง; ยังไม่ใช่ระบบขนส่งจริง |

มีเมนูบนหน้าจอไม่ได้แปลว่ามี API ส่วนกลางรองรับแล้ว เช่น เมนูแก้พนักงานของ Manager ยังเป็นเดโม่ และ API อ่านรายชื่อพนักงานเดิมยังไม่อนุญาต Manager จึงต้องกำหนดสิทธิ์ให้ตรงกันก่อนต่อส่วนกลาง

## 4. Login และการรับผู้ใช้ใหม่

- [x] แนวทางเดิมที่เจ้าของตกลง: ช่วงพัฒนาใช้บัญชีบริษัทและบัญชีเดโม่ได้; การตั้งค่าเดโม่ใช้เฉพาะ development
- [x] แนวทางเดิมที่เจ้าของตกลง: ปิดการผูก Microsoft กับพนักงานอัตโนมัติไว้ก่อน
- [x] เจ้าของยืนยัน: ผู้ใช้ที่ Login ครั้งแรกและยังไม่มี Role ต้องรอให้ Admin กำหนด Role เริ่มต้นเป็น Manager, Supervisor หรือ Employee ก่อนเข้าใช้งาน
- [x] เจ้าของยืนยันเพิ่มเติมวันที่ 12 พฤศจิกายน 2569 ว่า Manager รับช่วงจัดการพนักงานกะและหัวหน้ากะได้ครบ Shift A–D ทั้งย้ายทีม เปลี่ยนตำแหน่ง และเปลี่ยน Role ระหว่าง Employee กับ Supervisor การให้หรือถอน Role Manager และ Admin อยู่ที่ Admin
- [x] เจ้าของยืนยันว่าการย้ายทีมมีผลตั้งแต่วันที่ระบุ เช่น A ย้ายจาก Shift A ไป Shift B วันที่ 16 ตารางวันที่ 1–15 และประวัติการสลับกะหรือการลายังอ้างถึง Shift A ตั้งแต่วันที่ 16 ให้จัดกะตาม Shift B ตามขั้นตอนปรับตาราง
- [x] เจ้าของยืนยันให้ตรวจรายการที่กระทบก่อนบันทึกย้ายทีม ถ้ามีคำขอค้างของทีมเดิมที่เกี่ยวกับตารางตั้งแต่วันย้าย หรือมีผลอนุมัติเดิมที่ชนกับตารางทีมใหม่ ให้พักการย้ายและให้ผู้เกี่ยวข้องเคลียร์รายการก่อน ระบบไม่ยกเลิกคำขออัตโนมัติ
- [ ] ระบุวิธีจัดการรายการที่กติกาเดิมยกเลิกเองไม่ได้ และวิธีปรับกะที่ประกาศแล้วหรือชนกับผลอนุมัติเดิมโดยรักษาประวัติ
- [ ] Manager ทบทวนวิธียืนยันตัวพนักงานและทีมก่อนให้สิทธิ์ครั้งแรก
- [ ] ตรวจระบบ: คิวรอรับผู้ใช้ใหม่, Admin, การระงับ/คืนสิทธิ์ และหลักฐานการให้สิทธิ์ยังต้องพัฒนา

**สิ่งที่ระบบทำอยู่:** Login ยืนยันว่าเป็นใคร จากนั้น Backend ตรวจว่าบัญชีนั้นผูกกับผู้ใช้ที่ active และมี Role/ทีมใด ถ้ายังไม่ผูกจะได้ `ACCOUNT_NOT_LINKED` การเข้าสู่ Microsoft สำเร็จอย่างเดียวจึงยังไม่ให้สิทธิ์จัดกะ

Role ในแอป เช่น Manager/พนักงาน เป็นคนละเรื่องกับบัญชีเชื่อมฐานข้อมูล เช่น `tnc_backend_dev` การแก้ Role ในข้อมูลเดโม่หน้าเว็บไม่เปลี่ยนสิทธิ์จริงของ Backend

**รอคำตอบภายหลัง** ได้แก่ วิธีตั้ง Admin คนแรก ขั้นอนุมัติภายในก่อนให้หรือถอน Role ระดับสูง และนโยบายหลาย Role ในบัญชีเดียว

### ทดสอบกรณีเพื่อนมาทำแทนในวันหยุด

อ้างอิงตัวอย่างที่เจ้าของแจ้งในแชตวันที่ 10 พฤศจิกายน 2569 กรณีขอวันเดียวที่ผู้ยื่นมีกะและเพื่อนหยุดอยู่เดิม ให้ผลที่คาดหวังเป็น OT ของคนมาทำแทน

- [ ] ถ้าผู้ยื่นมีกะเช้า ให้หน้าตัวอย่างและตารางหลังอนุมัติแสดงผู้ยื่น `M → O` และคนแทน `O → MT`
- [ ] ถ้าผู้ยื่นมีกะดึก ให้หน้าตัวอย่างและตารางหลังอนุมัติแสดงผู้ยื่น `N → O` และคนแทน `O → NT`
- [ ] ตรวจว่าระหว่างรออนุมัติ ตารางทั้งคู่ยังใช้ค่าเดิม และหลังอนุมัติครบแล้วโหลดตารางใหม่ได้ผลตรงกับหน้าตัวอย่าง
- [ ] รอยืนยันประเภทคำขอ โควตา และสายอนุมัติสำหรับกรณีนี้ก่อนผูกกติกาเข้ากับ SW-04 ถึง SW-08 หรือใช้เส้นทาง OT แยก

ผลที่พบใน pilot คือฐานกลางยังมีเฉพาะ `M`, `N`, `O` หน้าตัวอย่างและ Backend จึงบันทึกคนแทนเป็น `M` หรือ `N` กรณี `MT` และ `NT` ยังไม่ผ่านเกณฑ์ข้างต้น

## 9. ข้อมูล สิทธิ์ และประวัติ

วัตถุประสงค์ตามฐานเดิมคือจัดตาราง พิจารณาคำขอ และตรวจสอบที่มา ใช้ข้อมูลขั้นต่ำ ได้แก่ ผู้ยื่น คู่สลับ ทีม Role วันที่ กะก่อน–หลัง สถานะ เวอร์ชัน ผู้ตัดสินและเวลา เหตุผลเก็บเท่าที่จำเป็น ไม่เพิ่มข้อมูลสุขภาพหรือข้อมูลใบลาในคำขอสลับ

- [ ] ตรวจสิทธิ์ที่ Backend ทุกคำสั่ง ไม่เชื่อ Role/ผู้ยื่นที่ browser ส่งมา
- [ ] ระบุขอบเขตที่แต่ละ Role อ่านได้ก่อนใช้ข้อมูลพนักงานจริง API เดโม่ปัจจุบันให้พนักงาน/หัวหน้า/Manager อ่านตารางทุกทีมได้ แต่ไม่ใช่นโยบายข้อมูลจริงที่อนุมัติแล้ว
- [ ] รักษาหลักฐานการส่ง ตัดสิน เปลี่ยนตาราง ถอน และการปฏิเสธสิทธิ์ โดยอ้างผู้กระทำและเวอร์ชันจริง
- [ ] บันทึกการให้สิทธิ์เข้าใช้และการเปลี่ยน Role เพื่อสอบทานสิทธิ์ ใช้รหัสผู้ได้รับสิทธิ์ ทีม Role ก่อน–หลัง ผู้ดำเนินการ และเวลา บังคับขอบเขต Admin และ Manager ตามหมวด 3–4
- [ ] เก็บ protected access/audit logs อย่างน้อย **90 วัน** ตาม `rule.md`; ไม่ใช้เลขนี้เป็นอายุจัดเก็บของข้อมูลทุกชนิด
- [ ] คงหลักฐานเดิมเมื่อแก้/ยกเลิก ไม่ลบหรือเขียนทับคำอนุมัติและตารางรุ่นก่อน
- [ ] อายุจัดเก็บคำขอ ข้อมูลพนักงาน บัญชีปิด และสิทธิ์อ่านประวัติ ต้องให้เจ้าของข้อมูลกำหนดเพิ่มเติม

pending ที่ทับช่องกะเดียวกัน: [ ] A ห้ามคำขอซ้อนช่องเดิม (ตรง API เดิม); [ ] B ให้ยื่นได้แล้วตรวจเวอร์ชันก่อนอนุมัติ (บางคำขออาจใช้ไม่ได้ภายหลัง); [ ] C ให้ผู้ยื่นถอน/แทนคำขอเดิมก่อน (ต้องเก็บประวัติการแทน)

หลังอนุมัติแล้ว ยกเลิกได้ก่อนช่วงงานแรกที่ได้รับผลเริ่ม เมื่อยกเลิกสำเร็จให้คืนตารางและค่าที่คำขอนั้นเปลี่ยนทั้งสี่ประเภทตามหมวด 6 กรณีปกติของการสลับกะให้ผู้ยื่นกดเอง กรณีมีคำขอใหม่เปลี่ยนช่องเดิมต่อยังเป็นคำถามเปิด

**การเปลี่ยนผ่านเมื่อมีการประกาศกฎใหม่ (เจ้าของยืนยันแล้ว)**

- [x] แจ้งวันเริ่มใช้ล่วงหน้า และเริ่มใช้เวลา 00:00 น. วันที่ 1 ตามเวลาไทย คำขอใหม่ตั้งแต่เวลานั้นใช้กฎใหม่ ซึ่งจะใช้ต่อไปจนกว่าจะมีการเปลี่ยนนโยบายอีกครั้ง
- [x] เก็บผลและประวัติของรายการที่อนุมัติครบก่อนเปลี่ยนกฎตามเดิม คำขอของเดือนก่อนที่ยังรออยู่ให้ปิดด้วยเหตุผล «ตารางเดือนปิดแล้ว» เก็บประวัติและไม่หักโควตา
- [x] ถ้ามีคำขอของเดือนใหม่ที่ยื่นไว้ก่อนเปลี่ยนกฎและยังรออยู่ ให้แจ้งผู้ยื่นล่วงหน้า ปิดรายการเดิมโดยคงประวัติและไม่หักโควตา แล้วให้ยื่นใหม่ภายใต้กฎใหม่

## 11. Checklist ลงมือหลังปิดกฎของรอบงานนั้น

- [ ] Manager ทบทวน SW-01–10 และคำตอบ Q ที่กระทบงานรอบแรก
- [ ] สรุปผลก่อน–หลังและสายอนุมัติที่ไม่กำกวมไว้ในไฟล์นี้
- [ ] วาง API/ข้อมูลโดยต่อยอด request ID, snapshot, version, audit และ idempotency เดิม
- [ ] ตรวจตารางทุกวันที่ได้รับผลรวมกัน และตรวจซ้ำก่อนอนุมัติสุดท้าย
- [ ] ตรวจโควตาของผู้ยื่นกับผลอนุมัติ/ตารางในธุรกรรมเดียว ป้องกันกดพร้อมกันเกินเพดาน
- [ ] ทดสอบการเริ่มรอบโควตาวันที่ 1 และให้ค่าที่ Manager เปลี่ยนมีผลในเดือนถัดไปทุกทีม เก็บหลักฐานผู้เปลี่ยน เวลาที่เปลี่ยน เดือนที่มีผล และค่าเดิมกับค่าใหม่
- [ ] บังคับเวลา 24 ชั่วโมงและเส้นตายของคำขอทั้งในคิวรอและตอนกดอนุมัติ ทดสอบตรงเวลาเส้นตายและกรณีอนุมัติค้างบางขั้น
- [ ] ทดสอบการล็อกตารางเมื่อขึ้นเดือนใหม่และการอ่านเพื่อสรุปของ HR ตามสิทธิ์
- [ ] ทดสอบ Admin ให้ Role ครั้งแรก และ Manager เปลี่ยน Role ที่อนุญาตในทีมของตน พร้อมตรวจการปฏิเสธเมื่ออยู่นอกขอบเขตและหลักฐานการเปลี่ยน
- [ ] ต่อฟอร์มและรายการคำขอให้ใช้ Supabase ผ่าน Backend ไม่ fallback เป็น local เมื่อบันทึกไม่สำเร็จ
- [ ] ทดสอบการเปลี่ยนกฎเวลา 00:00 น. วันที่ 1 ตาม Q5 ทั้งกรณีอนุมัติแล้ว ค้างของเดือนก่อน และยื่นล่วงหน้าสำหรับเดือนใหม่ พร้อมตรวจประวัติและโควตา
- [ ] ทดสอบหลายบัญชีที่แยก session และหลายเครื่อง พร้อมกรณีข้ามเดือน กะข้ามคืน ข้อมูลเก่า เครือข่ายขัดข้อง และ rollback
- [ ] เก็บผลทดสอบ/วันตรวจ แล้วจึงทำเครื่องหมาย “ตรวจระบบ” ของกฎที่ผ่านจริง

แนวทางเทคนิคที่เสนอ: ขยาย Backend/คำขอเดิมให้รองรับผลกระทบหลายวันที่อยู่ในคำขอเดียว มีรายละเอียดกะก่อน–หลังและเวอร์ชันของทุกช่อง อีกทางคือสร้างระบบคำขอใหม่แยก แต่จะมีสองคิวและต้องย้ายข้อมูลเพิ่ม จึงเสนอใช้ของเดิมต่อ ทั้งนี้โครงสร้างที่ขึ้นกับ Q1–Q5 ยังเป็นเงื่อนไข

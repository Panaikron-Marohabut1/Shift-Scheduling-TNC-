# Shift schedule TNC

## เอกสารกฎหลักสำหรับทบทวนก่อนพัฒนา

ใช้ [กฎและ Checklist ของระบบสำหรับ Manager](.docs/01-requirements/01-spec/2026-11-04-01-business-rules-master.md) เป็นไฟล์หลักสำหรับตรวจความเข้าใจ แก้กฎ และบันทึกคำตอบค้าง แยกการยืนยันกฎออกจากผลทดสอบโค้ด ก่อนเริ่มพัฒนารอบถัดไป

Alpha Demo วันที่ 7 ตุลาคม 2026: แอปสลับกะข้ามทีมบนเครื่อง ใช้ NestJS + TypeScript, PostgreSQL และ Vanilla JavaScript modules ข้อมูลทุกคนเป็นข้อมูลสมมติ ใช้สีและรูปแบบจากต้นแบบเดิมใน `prototypes/legacy-static/` ซึ่งยังเก็บไว้เป็นแหล่งอ้างอิง

## โครงสร้าง Project

- `apps/web/` — Frontend: หน้าจอเว็บจัดกะ
- `apps/api/` — Backend หลัก: ตรวจสิทธิ์ จัดการตารางกะ คำขอ และฐานข้อมูล
- `apps/auth/` — Backend สำหรับเข้าสู่ระบบ: เชื่อม Supabase Auth (เดิมอยู่ `shift/Backend/`)
- `prototypes/legacy-static/` — ต้นแบบเก่า พร้อมเอกสารออกแบบและรายงานตรวจเดิม
- `.docs/` — Requirements, design และคู่มือพัฒนา
- `scripts/` — เครื่องมือรันและตรวจ Project
- `.agents/`, `.codex/`, `.claude/` — Skills และการตั้งค่าของเครื่องมือ Agent
- `.local/`, `node_modules/`, `.env` — ข้อมูลและ dependencies เฉพาะเครื่อง ไม่เข้า Git

ดู [คู่มือโครงสร้างและ Agent](.docs/06-development/project-structure.md) สำหรับตำแหน่งที่แก้ไฟล์ร่วมกันและเหตุผลที่คงโฟลเดอร์ของแต่ละเครื่องมือ

ดู [ผลตรวจและข้อจำกัดก่อนส่งมอบวันที่ 1 พฤศจิกายน 2026](.docs/06-development/2026-11-01-release-check.md) สำหรับขอบเขต Login/โครงสร้าง ผลทดสอบ และปัญหา Logic เดิมที่ยังคงไว้ในรอบนี้

Frontend และ API เปิดด้วยกันที่ `http://localhost:3000` ส่วน Auth เปิดแยกที่ `http://localhost:3001` การแยกโฟลเดอร์บอกหน้าที่ของโค้ด ไม่ได้หมายความว่าต้องใช้เครื่อง Server คนละเครื่อง

### Milestone 1–3 ในเครื่อง

เปิดเว็บ, API และ Login ด้วย `pnpm dev` โควตาสลับกะ สายอนุมัติ วันหมดอายุ และตารางปิดเดือนสำหรับ HR ทำงานกับฐานเดโม่ใน `.env` หากฐานเดิมแจ้งว่า schema ยังเก่า ให้รัน `pnpm db:migrate` ก่อนเปิด

ฐานใหม่ที่เตรียมด้วย `pnpm db:seed` มีตารางสมมติตามรอบทีม A–D ตั้งแต่ 1 สิงหาคม 2569 ถึงสิ้นเดือนปัจจุบัน โดยรอบเดินต่อเนื่องข้ามเดือน หากต้องการสร้างฐานเดโม่ชุดใหม่ ให้ใช้ `pnpm demo:fresh` และผูกบัญชีทดสอบด้วย `pnpm link-user APP_USER_ID SUPABASE_AUTH_UID` ฐานที่ใช้ทดสอบอยู่แล้วสามารถนำค่าการเชื่อมต่อมาใช้ใน `.env` เพื่อเปิดต่อจากข้อมูลเดิมได้

ในฟอร์มสลับกะ เมื่อเลือกคู่และวันครบ ระบบแสดงผลตรวจจาก Backend และโควตาของผู้ยื่น ผลตรวจซ้ำตอนส่งและอนุมัติยังเป็นตัวตัดสิน หากมีคำขอเก่าที่ค้างจากก่อนใช้กฎนี้ ให้ปิดรายการตามสิทธิ์เดิมแล้วส่งคำขอใหม่ ตารางและประวัติที่อนุมัติแล้วเก็บตามเดิม

การเชื่อมฐานข้อมูล Supabase เป็นการตั้งค่าแยกจากฐานเดโม่ในเครื่อง ดู [สถานะฐานข้อมูล Supabase](.docs/06-development/2026-11-01-supabase-migration.md)

### ทดลองสลับกะร่วมกันใน Milestone 5

ใช้ `pnpm dev:supabase` เพื่อเปิดแอปในเครื่องของแต่ละคนและใช้ฐาน Supabase เดิมร่วมกันสำหรับสลับกะ เมนู Admin เดโม่ และการจัดการพนักงานโดย Manager ดู [วิธีตั้งค่าและทดสอบร่วมกัน](.docs/06-development/2026-11-13-remote-swap-pilot.md)

### ทดลอง Admin และ Manager ใน Milestone 4

ในฐานเดโม่เดิมให้รัน `pnpm db:migrate` แล้ว `pnpm db:seed` จากนั้นเปิดด้วย `pnpm dev` ใช้ `pnpm link-user` ดู `demo_profile` และ `user_id` ก่อนผูก UID ของบัญชี Supabase Auth สำหรับทดลอง

- ผูกบัญชี Admin กับ `admin-demo` แล้วเข้าเมนู **กำหนดบทบาท**
- ผูกบัญชีที่จะทดลองเข้าคิวกับ `employee-b2-onboarding` ให้บัญชีนี้เข้าแอปครั้งแรก จากนั้นเปิดคิวด้วย Admin และกำหนดบทบาทเริ่มต้น พนักงานเปิดแอปใหม่เพื่อใช้งานตามบทบาทที่ได้รับ
- บัญชี Manager เดโม่เปิดเมนู **พนักงานและทีม** เพื่อแก้ตำแหน่ง บทบาทระหว่าง Employee กับ Supervisor และย้ายทีมตามวันที่ ระบบเก็บทีมตามวันที่ในตารางเดิมและพักการเปลี่ยนเมื่อพบคำขอที่ต้องจัดการก่อน

การตั้ง Admin คนแรกและขั้นตอนให้หรือถอนสิทธิ์ระดับสูงของบัญชีบริษัทอยู่ใน [แผน Milestone 4](.docs/06-development/access-management-checkpoint.md#แผนเริ่ม-milestone-4--12-พฤศจิกายน-2569)

Auth ยังมี `package-lock.json` ของตัวเองและใช้ npm แยกจาก API แต่มีคำสั่งรวมให้รันจาก root ของโปรเจคแล้ว เมื่อตั้งค่าตาม [คู่มือ Auth](apps/auth/README.md):

```powershell
pnpm deps
pnpm dev
```

`pnpm deps` ติดตั้ง dependencies ทั้ง API และ Auth ใช้ครั้งแรกหรือหลัง Pull เมื่อ dependencies เปลี่ยน ส่วน `pnpm dev` เปิดฐานข้อมูลเดิม เว็บ/API และ Login ใน Terminal เดียว กด Ctrl+C เพื่อหยุดเว็บและ Login พร้อมฐานข้อมูลที่คำสั่งนี้เปิดให้ หากฐานข้อมูลเปิดอยู่ก่อนแล้ว จะคงไว้ตามเดิม คำสั่งนี้ไม่ migrate, seed หรือล้างข้อมูลอัตโนมัติ

หากต้องการเปิดแยก ใช้ `pnpm db:start`, `pnpm dev:api` และ `pnpm dev:auth` ตามเดิม โดยเปิด API กับ Auth คนละ Terminal

Workflow ที่ API รองรับ: เข้าสู่ระบบด้วยบัญชีที่ผูกกับพนักงานเดโม → ยื่นคำขอสลับวันเดียว → หัวหน้าทีมผู้ขออนุมัติ → หัวหน้าอีกทีมอนุมัติ → กะสองคนเปลี่ยนพร้อมกัน → Refresh → ตรวจประวัติ ส่วนแบบฟอร์มใหม่ที่มีวันคืนกะยังเก็บคำขอในเบราว์เซอร์ ตามข้อจำกัดในเอกสารผลตรวจข้างต้น

หากส่งวันที่หรือคู่สลับผิด พนักงานผู้ยื่นกด **ยกเลิกคำขอ** ใน “คำขอของฉัน” แล้วกดยืนยันได้ก่อนหัวหน้าคนแรกบันทึกคำตัดสิน แม้หัวหน้าเปิดตรวจแล้วก็ยังยกเลิกได้ หลังอนุมัติครั้งแรกจะยกเลิกไม่ได้ คำขอแสดง “ยกเลิกแล้ว” และมีประวัติ โดยตารางกะไม่เปลี่ยน สามารถยื่นคำขอใหม่สำหรับกะเดิมได้

## เริ่มบน Windows

1. ใน VS Code เลือก **File → Open Folder** แล้วเปิดโฟลเดอร์ `Shift-Scheduling-TNC-` ที่มี `package.json` ไม่เลือกโฟลเดอร์ `apps/` หรือ legacy prototype
2. เครื่องใหม่ให้ติดตั้ง [Node.js 24 LTS สำหรับ Windows](https://nodejs.org/en/download) แล้วเปิด Terminal ใหม่ ติดตั้ง pnpm รุ่นที่โปรเจคกำหนด:

```powershell
npm.cmd install --global pnpm@11.25.0
```

3. เลือก **Terminal → New Terminal** ที่ root ของ Project แล้วรันทีละคำสั่ง ระบบทดสอบด้วย Node.js 24 และ pnpm 11.25.0 บน Windows ใช้ชื่อคำสั่งลงท้าย `.cmd` ได้หาก PowerShell ไม่อนุญาต script launcher:

```powershell
pnpm deps
pnpm setup
pnpm db:migrate
pnpm db:seed
pnpm dev
```

ก่อน `pnpm dev` ให้เตรียม `apps/auth/.env.local` ตาม [คู่มือ Auth](apps/auth/README.md) ด้วย จากนั้นรอทั้งเว็บ/API และ Login พร้อม จึงเปิด URL ด้านล่างและเปิด Terminal ค้างไว้ `setup` เตรียม PostgreSQL ให้ ไม่ต้องติดตั้งฐานข้อมูลแยกหรือคัดลอก `.env.example` ก่อน

เปิด **http://localhost:3000** ใช้ URL นี้สำหรับคำสั่งเปลี่ยนข้อมูล เนื่องจากระบบตรวจ origin แบบตรงกัน Frontend และ `/api` ใช้ origin เดียวกัน

`setup` ดาวน์โหลด PostgreSQL 18.6 Windows x64 จาก EDB เฉพาะเมื่อยังไม่มี เตรียมฐานข้อมูลและรหัสผ่านสุ่มใน `.env` และคัดลอกฟอนต์สำหรับใช้ออฟไลน์ เก็บทั้งหมดในเครื่อง ไม่ติดตั้ง Windows service และไม่แก้ PATH ของระบบ PostgreSQL รับการเชื่อมต่อที่ `127.0.0.1:54329` เท่านั้น ครั้งแรกต้องมีอินเทอร์เน็ตและพื้นที่สำหรับ archive ประมาณ 400 MB พร้อมไฟล์ที่แตกแล้ว

ไม่ต้องคัดลอก `.env.example` ก่อนใช้ portable setup ไฟล์นี้เป็นตัวอย่างสำหรับผู้ที่เตรียม PostgreSQL เอง รหัสผ่านตัวอย่างใช้รันไม่ได้ Instance อื่นต้องเตรียม owner role และ runtime role `shiftflow_app` ที่เป็น non-superuser ให้ตรง migration ชื่อ role/database ภายในเป็นชื่อเทคนิคที่ใช้ก่อนเปลี่ยนชื่อผลิตภัณฑ์

## เปิดครั้งต่อไปและตรวจความพร้อม

### Windows ปฏิเสธพอร์ตด้วย `listen EACCES`

ตรวจพอร์ตที่ Windows สงวนไว้ด้วย `netsh interface ipv4 show excludedportrange protocol=tcp` หากพอร์ต 3000/3001 อยู่ในช่วงนั้น ให้ใช้พอร์ตที่ว่าง เช่น ตั้ง `PORT=4000`, `APP_ORIGIN=http://localhost:4000` และ `AUTH_URL=http://localhost:4001` ใน `.env` ที่ root พร้อมตั้ง `AUTH_HOST=http://localhost:4001` และ `TRUSTED_APP_ORIGINS=http://localhost:4000` ใน `apps/auth/.env.local` โดยคงค่า Supabase เดิมไว้

เปิดทั้งหมดด้วย `pnpm dev` คำสั่งอ่านพอร์ตและ callback origin จากการตั้งค่าข้างต้น แล้วเข้า `http://localhost:4000` หากใช้ Microsoft Login ต้องมี callback origin/URL ใหม่ที่ตรงกันใน Supabase Redirect URLs ด้วย การเปลี่ยนพอร์ตในเครื่องไม่แก้การตั้งค่า Supabase บน cloud

### เริ่มบริการ

```powershell
pnpm dev
```

เปิดแอปซ้ำไม่ล้างข้อมูล `db:seed` ทำงานเมื่อสั่งเท่านั้น เมื่อมีข้อมูลแล้วจะเพิ่ม/อัปเดตบัญชีเดโมโดยไม่ลบตาราง คำขอ หรือประวัติ ข้อมูลที่เชื่อม API เก็บใน PostgreSQL จึงยังอยู่หลัง Refresh และ restart Backend แต่คำขอใหม่หลายประเภทและการแก้ตารางใน Demo ยังเก็บใน localStorage และไม่แชร์ข้ามเครื่อง หลังอัปเดตโค้ดที่มี migration ใหม่ให้ปิด Backend แล้วรัน `pnpm db:migrate` และ `pnpm db:seed` ก่อนเปิดอีกครั้ง

```powershell
pnpm check
pnpm test
pnpm audit:backlog
```

`check` สร้าง Backend ตรวจ syntax JavaScript และโครงสร้าง Markdown ที่เปลี่ยน `test` ใช้ฐานข้อมูลแยกที่สร้างและลบเฉพาะของ suite ไม่ล้างเดโม ต้องเปิด PostgreSQL และมี `.env` ก่อน `audit:backlog` ตรวจ traceability ของ spec/backlog ปัจจุบันโดยไม่แก้เนื้อหา

`pnpm test:browser` เป็นชุดทดสอบ workflow เดิมที่ใช้ Playwright และ Chromium สร้างฐานทดสอบแยกบนพอร์ต 3021 โดยไม่เปลี่ยน `.env` หรือข้อมูลเดโม ปัจจุบันยังไม่ผ่าน เพราะอ้างหน้าเลือกบัญชี Demo ที่ถูกแทนด้วย Login แล้ว ต้องปรับชุดทดสอบให้ตรงระบบปัจจุบันก่อนใช้เป็นเกณฑ์ผ่านทั้งระบบ ตั้ง `PLAYWRIGHT_PACKAGE` และ `BROWSER_EXECUTABLE` หากใช้ package/browser ที่ติดตั้งไว้นอกโปรเจค รายละเอียดเดิมอยู่ใน [Alpha Demo implementation notes](.docs/02-design/prototype/alpha-demo.md)

สำหรับรันชุดที่ build แล้ว:

```powershell
pnpm build
pnpm start
```

ความพร้อมฐานข้อมูล: **http://localhost:3000/api/health** ถ้าฐานข้อมูลไม่พร้อม แอปจะไม่เปลี่ยนไปใช้ข้อมูลชั่วคราว กด Ctrl+C ใน Terminal ของ `pnpm dev` เพื่อหยุดบริการที่คำสั่งเปิดให้ หากเปิดฐานข้อมูลแยกไว้ก่อน ให้หยุดด้วย `pnpm db:stop` เมื่อเลิกใช้

## ซ้อมเดโม 4 นาที

เปิดทุกบริการด้วย `pnpm dev` แล้วเข้า http://localhost:3000 ระบบจะพาไปหน้าเข้าสู่ระบบของ `apps/auth` ที่ **http://localhost:3001** บัญชี Supabase ต้องผูกกับผู้ใช้ในฐานข้อมูลก่อน:

1. `pnpm link-user` แสดงผู้ใช้ทั้งหมด (`user_id` บทบาท ทีม และบัญชีที่ผูกแล้ว)
2. คัดลอก UID ของบัญชีจาก Supabase Dashboard → Authentication → Users
3. `pnpm link-user <user_id> <UID>` ผูกบัญชี (`pnpm link-user <user_id> --unlink` เพื่อยกเลิก) ทุกครั้งบันทึกใน audit

บัญชีที่เข้าสู่ระบบได้แต่ยังไม่ผูกจะเห็นข้อความ "บัญชีนี้ยังไม่ได้ผูกกับพนักงานในระบบ" และใช้ API ไม่ได้ (403)

1. เข้าเป็น **Shift Employee** เปิด “ตารางกะ” กดช่องกะของ **พนักงานทดสอบ B1** ในวันที่กะต่างกัน แล้วกด “สลับกะกับ …”
2. ตรวจผลในตารางและผลตรวจกฎ ส่งคำขอ แล้วเปิด “คำขอของฉัน” (Refresh แล้วคำขอยังอยู่)
3. ออกจากระบบ (กดชื่อมุมล่างซ้าย) เข้าเป็น **Shift Supervisor A** เปิด “คิวคำขอตรวจสอบ” กดอนุมัติ ตารางยังไม่เปลี่ยน
4. เข้าเป็น **Shift Supervisor B** อนุมัติขั้นที่สอง
5. กลับเป็น Shift Employee ดูตาราง ช่องที่สลับมีมุมแดง เปิด “คำขอของฉัน” ดูผลและผู้อนุมัติ ส่วน “ประวัติของฉัน” แสดงรายการของบัญชีตนพร้อมเวลา

มีตารางสมมติทีม A–D เดือนกันยายน–พฤศจิกายน 2026 เลือกเข้าใช้ได้ **9 บัญชี**: Manager, Supervisor 1–4 (A–D), Shift employee 1 (A), Shift employee 2 (B), HR และ External user พนักงาน A/B เลือกคู่สลับจากทีมอื่นใน A–D ได้เมื่อผ่านเงื่อนไขตำแหน่ง กะต่างกัน กะไม่ซ้อน และวันทำงานต่อเนื่อง หัวหน้าทีมผู้ขออนุมัติก่อน แล้วหัวหน้าทีมคู่สลับอนุมัติ บัญชีพนักงาน C/D ยังไม่เปิดเลือกใช้ ไม่คัดลอกชื่อหรือเบอร์ติดต่อจาก seed เก่า Browser tabs ใน profile เดียวใช้ cookie ร่วมกัน หากดูหลาย session พร้อมกันให้ใช้คนละ Browser profile หรือหน้าต่างปกติกับ private window

สำหรับฐานเดโมเดิม ให้รัน `pnpm db:migrate` แล้ว `pnpm db:seed` เพื่อเพิ่ม Supervisor C/D ในหน้าเลือกบัญชี คำสั่งรักษา user IDs ตาราง คำขอ และ audit เดิม ไม่ต้องใช้ `demo:fresh` ตัวอย่าง fixture: A1 → D1 วันที่ 8 ตุลาคม หรือ B1 → C1 วันที่ 11 ตุลาคม 2026 (หากกะในวันนั้นยังไม่ถูกเปลี่ยนจากการทดลองก่อนหน้า)

กะที่สลับและอนุมัติครบมีมุมแดงในช่องตาราง ชี้เมาส์หรือแตะช่องเพื่อดูกะก่อน–หลัง ทุกบัญชีที่อ่านตารางนั้นได้เห็นรายละเอียดนี้ตามขอบเขตเดิม HR อ่านเฉพาะตารางเผยแพร่ External ไม่มีสิทธิ์ แสดงที่มาของกะปัจจุบันเท่านั้นและยังเก็บประวัติเดิม การเพิ่มเครื่องหมายไม่ต้อง migrate หรือ seed เพิ่ม

หน้าเว็บมีความสามารถบางส่วนที่ระบบหลังบ้านยังไม่รองรับ (ลา OT เปลี่ยนวันหยุด เปลี่ยนกะ วันหยุดนักขัตฤกษ์ ประกาศตารางทั้งปี ฯลฯ) ส่วนนี้เก็บในเบราว์เซอร์ของเครื่องนั้นเป็นการชั่วคราว รายการและจุดที่ต้องต่อ API อยู่ใน [apps/web/README.md](apps/web/README.md)

หลังซ้อม หากต้องการ fixture ใหม่ ให้ปิด Backend แล้วรัน `pnpm demo:fresh` จากนั้นเปิดแอปอีกครั้ง คำสั่งสร้างฐานข้อมูลใหม่และเปลี่ยน `.env` โดย **เก็บฐานข้อมูลเก่าและประวัติทั้งหมดไว้** มีสำเนา config เก่าใน `.local/env-backups/` ไม่มีปุ่มล้างข้อมูลในหน้าจอและไม่มีงานลบ logs อัตโนมัติ ต้องเก็บหลักฐานอย่างน้อย 90 วัน การจัดการ retention จริงยังรอบริษัทอนุมัติ

## ขอบเขตและสิ่งที่รอบริษัท

- Demo account selector ใช้เฉพาะ localhost; session cookie เป็น HttpOnly, SameSite=Strict สิทธิ์ตรวจที่ Backend จาก IDs
- อนุมัติสองขั้นเป็นเส้นทางเดโมที่ผู้ใช้เลือก ยังไม่รับรอง authority บริษัท การอนุมัติผูก request version และ assignment snapshots
- ตรวจวันที่ ความเป็นเจ้าของ ต่างทีม ตำแหน่งใน fixture กะซ้อน และไม่เกิน 6 วันทำงานต่อเนื่องรวมข้ามเดือน
- โควต้า cutoff ช่วงเวลาคำขอ กำลังคนขั้นต่ำ และทักษะบริษัทแสดง “รอยืนยัน” ไม่อ้างว่าผ่านแล้ว
- Company Identity และ Power Apps มี interfaces ใน `apps/api/src/integrations/contracts.ts` ยังไม่มี provider, payload, sync หรือเส้นทางรับข้อมูลจริง โหมด COMPANY ถูกปิด
- Manager อ่านคำขอรวม พนักงาน/ทีม ตารางรายปี และตั้งค่า ไม่มีสิทธิ์อนุมัติ HR อ่านเฉพาะตารางที่เผยแพร่ External มีหน้ารับส่งที่ยังไม่โหลดข้อมูลภายใน
- หน้าตาม Prototype สำหรับ Leave/OT, HR export, รถรับส่งและจัดตารางรายปีเตรียมไว้แล้ว ส่วนที่ยังไม่เชื่อมปิดปุ่มและไม่สร้างผลสำเร็จจำลอง
